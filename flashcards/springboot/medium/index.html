@Bean vs @Component?

Quick Answer

@Component is for class-level scanning; @Bean is for method-level definition in @Configuration.

Detailed Explanation

@Component and @Bean both create Spring beans, but they differ in discovery and configuration. @Component uses classpath scanning to auto-detect classes, while @Bean provides explicit method-level configuration in @Configuration classes. Internally, both register beans in the application context, but @Bean allows more control over instantiation and third-party classes. Best practices include using @Component for your code and @Bean for external libraries. Common pitfalls include circular dependencies and improper scoping. Real-world usage includes configuring data sources, REST templates, and custom beans. Performance considerations involve bean creation timing and proxy overhead.

@Bean vs @Component?

Quick Answer

Method-level vs Class-level.

Detailed Explanation

@Component is for auto-scanned classes you own. @Bean is for method-returned objects, often third-party or conditional. Both create Spring beans.

Internal Mechanics: @Component uses classpath scanning. @Bean methods are called during configuration. Both register in ApplicationContext.

Recommended Practices: Use @Component for your classes. Use @Bean for third-party classes or complex initialization.

Common Mistakes: Using @Component on third-party classes. Overusing @Bean when @Component suffices.

Practical Use Cases: @Component for services, repositories. @Bean for DataSource, RestTemplate.

Performance Implications: Scanning can slow startup. @Bean methods called once per context.

@ConditionalOnProperty?

Quick Answer

Loads a bean only if a property is present/matches.

Detailed Explanation

@ConditionalOnProperty is part of Spring Boot's conditional configuration system, allowing beans to be registered only when specific properties are set to certain values. It's extensively used in auto-configuration to enable/disable features based on application properties.

Internal Mechanics: During bean registration, Spring evaluates the condition by checking the property value against the specified criteria. If the condition fails, the bean is not registered. This happens during the configuration phase, before the application context is fully initialized.

Recommended Practices: Use for feature toggles and optional integrations. Combine with @ConditionalOnClass for classpath-based conditions. Document the required properties in configuration metadata.

Common Mistakes: Using it for runtime decisions instead of configuration-time. Not providing default values, causing confusion when properties are missing.

Practical Use Cases: Enable/disable caching based on 'app.caching.enabled=true'. Configure different authentication providers based on 'auth.provider=oauth2'.

Performance Implications: Conditions are evaluated once at startup, so no runtime overhead. However, complex conditions or many conditional beans can slow startup time.

@ConfigurationProperties?

Quick Answer

Type-safe config.

Detailed Explanation

@ConfigurationProperties binds external configuration properties to strongly-typed Java objects, providing type safety and validation. Internally, Spring uses property sources and converters to map properties to bean fields, supporting nested objects and lists. Best practices include using validation annotations, prefixing properties logically, and enabling configuration metadata for IDE support. Common pitfalls include forgetting to enable configuration properties scanning or using incorrect property names. In real-world scenarios, it's used for database configurations, external API credentials, and feature flags. Performance considerations are minimal as binding occurs at startup, but avoid deep nesting for complex configurations.

@PathVariable vs @RequestParam?

Quick Answer

URI path segment vs Query parameter.

Detailed Explanation

@PathVariable and @RequestParam are both used to extract values from HTTP requests, but they serve different purposes in REST API design. Internally, Spring's request mapping mechanism parses the URI and query string to populate these parameters. @PathVariable extracts values from the URI path template, making them part of the resource identifier, while @RequestParam extracts from the query string for optional parameters. Best practices include using path variables for required resource identifiers and query params for filtering/sorting. Common pitfalls include forgetting to URL-encode path variables and confusing optional vs required parameters. Real-world usage includes RESTful APIs with resource hierarchies and search/filtering capabilities. Performance considerations are minimal as parsing happens once per request.

Code Example
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.http.ResponseEntity;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import java.util.List;
import java.util.Optional;

@RestController
public class UserController {
    
    @Autowired
    private UserService userService;
    
    // Path variable for required resource ID
    @GetMapping("/users/{id}")
    public ResponseEntity<User> getUser(@PathVariable Long id) {
        Optional<User> user = userService.findById(id);
        if (user.isPresent()) {
            return ResponseEntity.ok(user.get());
        } else {
            return ResponseEntity.notFound().build();
        }
    }
    
    // Multiple path variables for nested resources
    @GetMapping("/users/{userId}/orders/{orderId}")
    public ResponseEntity<Order> getUserOrder(
            @PathVariable Long userId,
            @PathVariable Long orderId) {
        
        Optional<Order> order = userService.findOrderByUserAndId(userId, orderId);
        return order.map(ResponseEntity::ok)
                   .orElse(ResponseEntity.notFound().build());
    }
    
    // Query parameters for filtering and pagination
    @GetMapping("/users")
    public Page<User> getUsers(
            @RequestParam(required = false) String name,
            @RequestParam(required = false) String email,
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "10") int size,
            @RequestParam(defaultValue = "name") String sortBy) {
        
        return userService.findUsers(name, email, PageRequest.of(page, size, Sort.by(sortBy)));
    }
    
    // Optional query parameters with default values
    @GetMapping("/search")
    public List<User> searchUsers(
            @RequestParam String query,
            @RequestParam(defaultValue = "name") String searchField,
            @RequestParam(defaultValue = "false") boolean caseSensitive) {
        
        return userService.searchUsers(query, searchField, caseSensitive);
    }
    
    // Path variable with regex validation
    @GetMapping("/users/{id:[0-9]+}")
    public User getUserByNumericId(@PathVariable Long id) {
        // Only accepts numeric IDs
        return userService.findById(id)
            .orElseThrow(() -> new UserNotFoundException("User not found: " + id));
    }
}

    private UserRepository userRepository;

    }

        return orderRepository.findByUserIdAndId(userId, orderId);
    }
    
    public Page<User> findUsers(String name, String email, Pageable pageable) {
        if (name != null && email != null) {
            return userRepository.findByNameContainingAndEmailContaining(name, email, pageable);
        } else if (name != null) {
            return userRepository.findByNameContaining(name, pageable);
        } else if (email != null) {
            return userRepository.findByEmailContaining(email, pageable);
        } else {
            return userRepository.findAll(pageable);
        }
    }
    
    public List<User> searchUsers(String query, String field, boolean caseSensitive) {
        // Implementation with proper escaping and validation
        if (!isValidSearchField(field)) {
            throw new IllegalArgumentException("Invalid search field: " + field);
        }
        
        return userRepository.searchByField(query, field, caseSensitive);
    }
    
    private boolean isValidSearchField(String field) {
        return Arrays.asList("name", "email").contains(field);
    }
}

@PreAuthorize annotation.

Quick Answer

Enables method-level security using SpEL expressions.

Detailed Explanation

@PreAuthorize provides method-level security by evaluating Spring Expression Language (SpEL) expressions before method execution. It requires @EnableMethodSecurity (or @EnableGlobalMethodSecurity in older versions). Internally, it uses AOP proxies to intercept method calls. If the expression evaluates to false, an AccessDeniedException is thrown.

Best practices: 1) Use for fine-grained authorization. 2) Combine with @PostAuthorize for post-execution checks. 3) Leverage built-in expressions like hasRole(). Common pitfalls: performance overhead, complex expressions, or forgetting to enable method security. Real-world usage includes protecting sensitive operations and implementing role-based access. Performance considerations include caching authentication context.

DataJPQL

@Query annotation usage.

Quick Answer

Used to define custom JPQL or Native SQL queries on repository methods.

Detailed Explanation

The @Query annotation in Spring Data JPA allows developers to define custom queries using JPQL (Java Persistence Query Language) or native SQL, providing more flexibility than method name-based queries. Internally, Spring Data parses the annotation at runtime, creates the appropriate query, and executes it against the underlying JPA provider (like Hibernate). JPQL operates on entities and their relationships, while native SQL works directly with database tables. This is particularly useful for complex joins, aggregations, or database-specific functions that can't be expressed through method naming conventions.

Best practices include: 1) Use JPQL for portability across databases. 2) Prefer named parameters over positional ones for readability. 3) Use @Modifying for update/delete operations. 4) Leverage @QueryHints for performance optimization. Common pitfalls: forgetting to handle null parameters, not using pagination for large result sets, or mixing JPQL with native SQL inappropriately. Real-world usage includes reporting queries, complex search filters, and bulk operations. Performance considerations involve indexing database columns used in queries, using COUNT queries for pagination, and avoiding N+1 query problems by using JOIN FETCH or entity graphs.

@Service vs @Repository?

Quick Answer

Semantic difference + Exception translation.

Detailed Explanation

@Service is used to mark classes that contain business logic, making them candidates for Spring's component scanning and dependency injection. It serves as a semantic marker for service layer components. @Repository is specifically for data access objects (DAOs) and enables automatic exception translation from lower-level persistence exceptions (like JDBC's SQLException or JPA's PersistenceException) to Spring's DataAccessException hierarchy. This translation provides a consistent exception model across different persistence technologies.

Internal Mechanics: Both annotations are stereotypes that trigger component scanning, but @Repository additionally registers a PersistenceExceptionTranslationPostProcessor that wraps bean methods with exception translation logic. The translation happens through AOP proxies that catch and convert exceptions.

Recommended Practices: Use @Service for business logic classes and @Repository only for data access. Avoid mixing concerns by not using @Repository on service classes. For custom repositories, extend Spring Data interfaces.

Common Mistakes: Using @Repository on service classes leads to unnecessary exception translation overhead. Forgetting to handle translated exceptions properly can mask underlying issues.

Practical Use Cases: In a layered architecture, @Service handles user registration logic (validation, email sending), while @Repository manages database operations (CRUD on User entities).

Performance Implications: Exception translation adds minimal overhead but can be bypassed by using @Repository judiciously. Avoid catching and re-throwing exceptions unnecessarily in repository methods.

@Repository

    private EntityManager entityManager;

    public User save(User user) {
        try {

                entityManager.persist(user);
                return user;
            } else {
                return entityManager.merge(user);
            }
        } catch (Exception e) {
            // Exception translation will convert this to DataAccessException
            throw e;
        }
    }

    public boolean existsByEmail(String email) {
        try {
            return entityManager.createQuery("SELECT COUNT(u) FROM User u WHERE u.email = :email", Long.class)
                    .setParameter("email", email)
                    .getSingleResult() > 0;
        } catch (Exception e) {
            throw e; // Will be translated
        }

Atomic operations.

Bean Scopes?

Quick Answer

Singleton, Prototype, Request...

Detailed Explanation

Bean scopes in Spring define the lifecycle and sharing of bean instances. Singleton (default) creates one instance per container, shared across the application. Prototype creates a new instance for each injection or lookup. Request and Session scopes are web-aware, creating instances per HTTP request or session. Internally, the BeanFactory manages scope-specific storage and retrieval. Best practices include using Singleton for stateless services, Prototype for stateful objects, and web scopes for request-specific data. Performance considerations: Singleton is most efficient, but Prototype can lead to object creation overhead; web scopes consume memory per request.

Recommended Practices: Refactor to eliminate cycles. Use @Lazy as temporary fix. Consider event-driven communication.

Quick Answer

Cross-Origin Resource Sharing. Must be enabled if frontend is on a different domain.

Real-world scenarios include single-page applications served from different domains, API gateways, and microservices communication. Performance considerations are minimal, but improper configuration can lead to unnecessary preflight requests.

Explain Profiles in Spring Boot.

Quick Answer

Profiles provide a way to segregate parts of your application configuration and make it available only in certain environments (e.g., dev, test, prod).

Detailed Explanation

Spring Profiles allow environment-specific configuration management by enabling or disabling beans and configuration properties based on the active profile. Internally, Spring evaluates @Profile annotations and property sources during context initialization, loading only relevant configurations to optimize memory and startup time. Profiles support inheritance through profile groups (Spring Boot 2.4+) and can be activated programmatically via ConfigurableEnvironment or declaratively via spring.profiles.active. Best practices include using profiles for environment-specific settings like database connections, logging levels, and feature flags, while avoiding profile-specific business logic. Common pitfalls include forgetting to set active profiles in production, leading to incorrect configurations, and overusing profiles for what should be runtime properties. In real-world scenarios, profiles enable seamless deployment across dev/staging/prod environments, support A/B testing by toggling feature beans, and facilitate multi-tenant applications. Performance considerations include faster startup times with fewer loaded beans and reduced memory footprint in production profiles.

Filter vs Interceptor?

Quick Answer

Servlet spec vs Spring MVC.

Detailed Explanation

Filters are part of Servlet specification, intercepting all requests before they reach servlets. Interceptors are Spring-specific, working within Spring MVC context. Filters are more general, interceptors more integrated.

Internal Mechanics: Filters use FilterChain, interceptors use HandlerExecutionChain. Filters wrap the entire request, interceptors only Spring MVC requests.

Recommended Practices: Use filters for global concerns (security, compression), interceptors for Spring-specific logic (handler manipulation).

Common Mistakes: Using interceptors for non-Spring MVC requests. Heavy processing in filters affecting all requests.

Practical Use Cases: Filters for CORS, logging all requests; interceptors for controller-specific logic.

Performance Implications: Filters execute for all requests, use judiciously. Interceptors only for MVC requests.

// Filter example - CORS handling
@Component
public class CorsFilter extends OncePerRequestFilter {
    
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) 
            throws ServletException, IOException {
        
        // Set CORS headers for all requests
        response.setHeader("Access-Control-Allow-Origin", "*");
        response.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS");
        response.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization");
        response.setHeader("Access-Control-Max-Age", "3600");
        
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            response.setStatus(HttpServletResponse.SC_OK);
            return; // Don't continue the chain for OPTIONS requests
        }
        
        // Continue the filter chain
        filterChain.doFilter(request, response);
    }
}

@Component
public class RequestLoggingFilter implements Filter {
    private static final Logger logger = LoggerFactory.getLogger(RequestLoggingFilter.class);

    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        logger.info("RequestLoggingFilter initialized");
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) 
            throws IOException, ServletException {
        
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        
        long startTime = System.currentTimeMillis();
        
        logger.info("Request: {} {} from {}", 
            httpRequest.getMethod(), 
            httpRequest.getRequestURI(), 
            httpRequest.getRemoteAddr());
        
        try {
            chain.doFilter(request, response);
        } finally {
            long duration = System.currentTimeMillis() - startTime;
            logger.info("Response: {} in {}ms", httpResponse.getStatus(), duration);
        }
    }

    @Override
    public void destroy() {
        logger.info("RequestLoggingFilter destroyed");
    }
}

// Filter example - Authentication
@Component
public class AuthenticationFilter implements Filter {
    private final TokenService tokenService;

    public AuthenticationFilter(TokenService tokenService) {
        this.tokenService = tokenService;
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) 
            throws IOException, ServletException {
        
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        
        String token = httpRequest.getHeader("Authorization");
        
        try {
            if (token != null && token.startsWith("Bearer ")) {
                User user = tokenService.validateToken(token.substring(7));
                httpRequest.setAttribute("authenticatedUser", user);
            }
            // Continue even if no token - let controllers handle authorization
            chain.doFilter(request, response);
        } catch (TokenValidationException e) {
            httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            httpResponse.getWriter().write("Invalid token");
        }
    }
}

Global Exception Handling?

Quick Answer

@ControllerAdvice + @ExceptionHandler.

Detailed Explanation

@ControllerAdvice creates a global exception handler that intercepts exceptions thrown from any controller. @ExceptionHandler methods define how to handle specific exception types, allowing centralized error processing and consistent API responses.

Internal Mechanics: Spring MVC's HandlerExceptionResolver chain includes ExceptionHandlerExceptionResolver, which scans for @ExceptionHandler methods in @ControllerAdvice classes. Exceptions bubble up until caught.

Recommended Practices: Use for cross-cutting concerns like validation errors, security exceptions. Return consistent error response formats. Log exceptions appropriately.

Common Mistakes: Catching generic Exception masks specific handling. Not including stack traces in development but excluding in production.

Practical Use Cases: Handle validation errors with 400 status, authentication failures with 401, general errors with 500. Customize responses for REST APIs vs web pages.

Performance Implications: Minimal overhead as exceptions are rare. However, avoid throwing exceptions for normal flow control.

Code Example
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ControllerAdvice;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.context.request.WebRequest;
import org.springframework.validation.FieldError;
import javax.validation.ConstraintViolationException;
import java.util.HashMap;
import java.util.Map;
import java.time.LocalDateTime;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@ControllerAdvice
public class GlobalExceptionHandler {
    private static final Logger logger = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ResponseEntity<ErrorResponse> handleValidationExceptions(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getAllErrors().forEach((error) -> {
            String fieldName = ((FieldError) error).getField();
            String errorMessage = error.getDefaultMessage();
            errors.put(fieldName, errorMessage);
        });
        
        ErrorResponse errorResponse = new ErrorResponse(
            "VALIDATION_ERROR",
            "Validation failed for request",
            errors
        );
        
        logger.warn("Validation error: {}", errors);
        return ResponseEntity.badRequest().body(errorResponse);
    }

    @ExceptionHandler(ConstraintViolationException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ResponseEntity<ErrorResponse> handleConstraintViolationException(ConstraintViolationException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getConstraintViolations().forEach(violation -> {
            String fieldName = violation.getPropertyPath().toString();
            String message = violation.getMessage();
            errors.put(fieldName, message);
        });
        
        ErrorResponse errorResponse = new ErrorResponse(
            "CONSTRAINT_VIOLATION",
            "Constraint violation occurred",
            errors
        );
        
        logger.warn("Constraint violation: {}", errors);
        return ResponseEntity.badRequest().body(errorResponse);
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ResponseEntity<ErrorResponse> handleResourceNotFoundException(ResourceNotFoundException ex, WebRequest request) {
        ErrorResponse errorResponse = new ErrorResponse(
            "RESOURCE_NOT_FOUND",
            ex.getMessage(),
            null
        );
        
        logger.info("Resource not found: {}", ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponse);
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ResponseEntity<ErrorResponse> handleGlobalException(Exception ex, WebRequest request) {
        ErrorResponse errorResponse = new ErrorResponse(
            "INTERNAL_SERVER_ERROR",
            "An unexpected error occurred",
            null
        );
        
        logger.error("Unexpected error: ", ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(errorResponse);
    }

    // Custom exception class
    public static class ResourceNotFoundException extends RuntimeException {
        public ResourceNotFoundException(String message) {
            super(message);
        }
    }

    // Error response DTO
    public static class ErrorResponse {
        private String errorCode;
        private String message;
        private Map<String, String> fieldErrors;
        private LocalDateTime timestamp;

        public ErrorResponse(String errorCode, String message, Map<String, String> fieldErrors) {
            this.errorCode = errorCode;
            this.message = message;
            this.fieldErrors = fieldErrors;
            this.timestamp = LocalDateTime.now();
        }

        // Getters and setters
        public String getErrorCode() { return errorCode; }
        public String getMessage() { return message; }
        public Map<String, String> getFieldErrors() { return fieldErrors; }
        public LocalDateTime getTimestamp() { return timestamp; }
    }
}

How does @Transactional work?

Quick Answer

It wraps the method execution in a database transaction context.

Detailed Explanation

@Transactional uses AOP proxies to manage transactions, starting transactions on method entry and committing/rolling back on exit. Internally, Spring integrates with transaction managers (JPA, JDBC) and supports propagation, isolation, and timeout settings. Best practices include keeping transactions short, using read-only for queries, and proper exception handling. Common pitfalls include calling transactional methods from within the same class (proxy bypass) and long-running transactions causing locks. Real-world scenarios include ensuring data consistency in multi-step operations and implementing saga patterns. Performance considerations involve transaction overhead and deadlock prevention.

Code Example

import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.stereotype.Service;

@Service
public class BankService {
private final AccountRepository accountRepository;

public BankService(AccountRepository accountRepository) {
    this.accountRepository = accountRepository;
}

// Basic transactional method
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    Account from = accountRepository.findById(fromId)
        .orElseThrow(() -> new IllegalArgumentException("From account not found"));
    Account to = accountRepository.findById(toId)
        .orElseThrow(() -> new IllegalArgumentException("To account not found"));
    
    if (from.getBalance().compareTo(amount) < 0) {
        throw new InsufficientFundsException("Insufficient funds");
    }
    
    from.setBalance(from.getBalance().subtract(amount));
    to.setBalance(to.getBalance().add(amount));
    
    accountRepository.save(from);

SecurityJWT

Implement a JWT Authentication Filter.

Quick Answer

Intercepts requests, extracts 'Authorization: Bearer' token, validates it, and sets the SecurityContext.

Detailed Explanation

The JWT Authentication Filter is a critical component in securing Spring Boot applications using JSON Web Tokens. Internally, it extends OncePerRequestFilter to ensure it's executed once per request. The filter intercepts incoming HTTP requests, extracts the JWT from the 'Authorization' header (typically in the format 'Bearer '), and validates the token using a JWT provider. If the token is valid, it creates a UsernamePasswordAuthenticationToken with the user's details and authorities, then sets it in the SecurityContextHolder to establish the security context for the current thread. This allows subsequent parts of the application to access the authenticated user's information.

Best practices include: 1) Always validate the token's signature, expiration, and issuer. 2) Handle token refresh scenarios gracefully. 3) Use HTTPS to prevent token interception. 4) Implement proper error handling for invalid or expired tokens. Common pitfalls include: forgetting to clear the security context on logout, not handling token expiration properly, or exposing sensitive information in the token payload. In real-world scenarios, this filter is essential for stateless authentication in microservices architectures. Performance considerations involve caching user details to avoid repeated database lookups, and using efficient JWT libraries like JJWT or Nimbus JOSE for parsing and validation.

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.web.filter.OncePerRequestFilter;
import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.List;
import java.util.stream.Collectors;

public class JwtAuthenticationFilter extends OncePerRequestFilter {

private final JwtProvider jwtProvider;

public JwtAuthenticationFilter(JwtProvider jwtProvider) {
    this.jwtProvider = jwtProvider;
}

@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
        throws ServletException, IOException {
    try {
        String token = resolveToken(request);
        if (token != null && jwtProvider.validateToken(token)) {
            Authentication authentication = jwtProvider.getAuthentication(token);
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
    } catch (Exception e) {
        // Log the error and clear security context
        SecurityContextHolder.clearContext();
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        return;
    }
    filterChain.doFilter(request, response);
}

private String resolveToken(HttpServletRequest request) {
    String bearerToken = request.getHeader("Authorization");
    if (bearerToken != null && bearerToken.startsWith("Bearer ")) {
        return bearerToken.substring(7);
    }
    return null;
}

}

// JwtProvider class for demonstration
class JwtProvider {
private String secret = "your-secret-key"; // In production, use environment variables

public boolean validateToken(String token) {
    try {
        Jwts.parser().setSigningKey(secret).parseClaimsJws(token);
        return true;
    } catch (Exception e) {
        return false;
    }
}

public Authentication getAuthentication(String token) {
    Claims claims = Jwts.parser().setSigningKey(secret).parseClaimsJws(token).getBody();
    String username = claims.getSubject();
    List<String> roles = (List<String>) claims.get("roles");
    List<SimpleGrantedAuthority> authorities = roles.stream()
            .map(SimpleGrantedAuthority::new)
            .collect(Collectors.toList());
    return new UsernamePasswordAuthenticationToken(username, null, authorities);
}

}

RestTemplate vs WebClient?

Quick Answer

Blocking (Legacy) vs Non-blocking (Modern).

Detailed Explanation

RestTemplate uses blocking I/O, suitable for simple synchronous calls. WebClient uses reactive streams for non-blocking I/O, better for high-concurrency and streaming. RestTemplate is synchronous, WebClient is asynchronous.

Internal Mechanics: RestTemplate uses HttpURLConnection or Apache HttpClient. WebClient uses Reactor Netty with event loops.

Recommended Practices: Use WebClient for new applications, especially reactive stacks. Keep RestTemplate for legacy or simple cases.

Common Mistakes: Using RestTemplate in reactive applications causes blocking. Not handling WebClient's Mono/Flux properly.

Practical Use Cases: RestTemplate for simple REST calls, WebClient for microservices communication, streaming APIs.

Performance Implications: WebClient scales better under load. RestTemplate blocks threads, limiting concurrency.

Spring Bean Scopes?

Quick Answer

Singleton (default), Prototype, Request, Session, Application.

Detailed Explanation

Bean scopes define the lifecycle and sharing model of Spring beans. Singleton creates one instance per container, Prototype creates new instances on each request, and web scopes (Request, Session, Application) are tied to HTTP lifecycle.

Internal Mechanics: Scopes are managed by BeanFactory implementations. Singleton beans are stored in a map within the application context. Prototype beans are created fresh each time. Web scopes use thread-local storage or session attributes.

Recommended Practices: Use Singleton for stateless services, Prototype for stateful objects. Be cautious with web scopes due to serialization requirements in clustered environments.

Common Mistakes: Using Singleton for stateful beans leads to data corruption. Not understanding that Prototype beans don't receive lifecycle callbacks.

Practical Use Cases: Singleton for UserService, Prototype for shopping carts, Request scope for user context, Session for user preferences.

Performance Implications: Singleton is most efficient but can cause memory leaks if misused. Prototype creates more objects, increasing GC pressure. Web scopes add overhead in distributed systems.

Spring Data Projections?

Quick Answer

Fetching only a subset of columns/fields instead of the full entity.

Detailed Explanation

Spring Data Projections allow fetching only specific fields from entities, reducing memory usage and improving performance by avoiding loading unnecessary data. Internally, Spring Data generates queries that select only the projected fields, and at runtime, it creates proxy objects implementing the projection interface. There are interface-based, class-based, and dynamic projections. Interface-based projections use getter methods, while class-based use DTOs with constructors.

Best practices: 1) Use for read-only operations. 2) Prefer interface projections for simplicity. 3) Use @Value for computed fields. 4) Combine with pagination. Common pitfalls: trying to modify projected objects, forgetting to include required fields, or using projections inappropriately for complex mappings. Real-world usage includes API responses, search results, and dashboard data. Performance benefits are significant for large entities with many relationships, reducing database load and network traffic.

What are Profiles?

Quick Answer

Way to segregate application configuration.

Detailed Explanation

Spring Profiles allow you to define different configurations for different environments (dev, test, prod) or use cases. They enable conditional bean registration and property loading based on active profiles. Profiles can be activated via properties, environment variables, JVM arguments, or programmatically.

Internal Mechanics: During application startup, Spring scans for @Profile annotations on beans and only registers those matching active profiles. Property files are loaded in order: application.properties, then profile-specific ones (application-{profile}.properties), with later files overriding earlier ones.

Recommended Practices: Use profiles for environment-specific configurations like database connections, logging levels, and feature toggles. Avoid using profiles for business logic branching; use them for infrastructure concerns.

Common Mistakes: Hardcoding profile names in code instead of using properties. Not setting default profiles, leading to unexpected behavior in different environments.

Practical Use Cases: Use 'dev' profile for H2 in-memory database and relaxed security, 'prod' for PostgreSQL and full security. Feature flags can use profiles to enable/disable new features.

Performance Implications: Profile resolution happens at startup, so it doesn't affect runtime performance. However, loading unnecessary beans in wrong profiles can increase memory usage and startup time.

What defines a Transaction?

Quick Answer

@Transactional annotation.

Detailed Explanation

@Transactional marks methods that should run within a database transaction. Ensures ACID properties: Atomicity, Consistency, Isolation, Durability. Rollback on RuntimeException by default.

Internal Mechanics: Uses AOP to wrap methods with TransactionInterceptor. Creates proxy that manages transaction lifecycle using PlatformTransactionManager.

Recommended Practices: Use on service methods, not repositories. Specify rollback rules. Use read-only for queries. Choose appropriate isolation levels.

Common Mistakes: Applying to private methods (AOP won't work). Not handling checked exceptions. Nested transactions with wrong propagation.

Practical Use Cases: Money transfers, order processing, user registration with multiple DB operations.

Performance Implications: Transactions add overhead. Use minimal scopes. Read-only transactions skip dirty checks.

Code Example
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.TransactionSystemException;
import org.springframework.stereotype.Service;
import org.springframework.beans.factory.annotation.Autowired;

@Service
public class BankingService {
    private final AccountRepository accountRepository;
    private final TransactionRepository transactionRepository;

    @Autowired
    public BankingService(AccountRepository accountRepository, TransactionRepository transactionRepository) {
        this.accountRepository = accountRepository;
        this.transactionRepository = transactionRepository;
    }

    // Basic transactional method - rolls back on RuntimeException
    @Transactional
    public void transferMoney(Long fromAccountId, Long toAccountId, double amount) {
        Account fromAccount = accountRepository.findById(fromAccountId)
            .orElseThrow(() -> new AccountNotFoundException("Source account not found"));
        
        Account toAccount = accountRepository.findById(toAccountId)
            .orElseThrow(() -> new AccountNotFoundException("Destination account not found"));
        
        if (fromAccount.getBalance() < amount) {
            throw new InsufficientFundsException("Insufficient funds for transfer");
        }
        
        // Debit source account
        fromAccount.setBalance(fromAccount.getBalance() - amount);
        accountRepository.save(fromAccount);
        
        // Credit destination account
        toAccount.setBalance(toAccount.getBalance() + amount);
        accountRepository.save(toAccount);
        
        // Record transaction
        TransactionRecord record = new TransactionRecord(fromAccountId, toAccountId, amount, TransactionType.TRANSFER);
        transactionRepository.save(record);
    }

    // Read-only transaction for queries
    @Transactional(readOnly = true)
    public Account getAccountDetails(Long accountId) {
        return accountRepository.findById(accountId)
            .orElseThrow(() -> new AccountNotFoundException("Account not found"));
    }

    // Custom rollback rules
    @Transactional(rollbackFor = {InsufficientFundsException.class, AccountNotFoundException.class})
    public void processPayment(Long accountId, double amount) throws PaymentException {
        try {

What is @Async?

Quick Answer

Executes method in a separate thread.

Detailed Explanation

@Async enables asynchronous method execution using a thread pool. Methods return CompletableFuture, Future, or void. Requires @EnableAsync and proper configuration.

Internal Mechanics: Uses AOP to proxy methods, submitting them to TaskExecutor. Default executor is SimpleAsyncTaskExecutor, but should be configured for production.

Recommended Practices: Use for I/O bound operations. Configure custom executors. Handle exceptions properly. Avoid for CPU-intensive tasks.

Common Mistakes: Not configuring thread pools (unlimited threads). Forgetting exception handling. Using in transactional contexts incorrectly.

Practical Use Cases: Email sending, file processing, external API calls, report generation.

Performance Implications: Better resource utilization for I/O operations. Thread pool configuration crucial to prevent exhaustion.

What is @Value?

Quick Answer

Annotation to inject values from properties files into variables.

Detailed Explanation

@Value is a Spring annotation that enables dependency injection of values from various sources into bean properties. Internally, it works through Spring's property resolution mechanism, which checks multiple property sources in order: system properties, environment variables, application.properties files, and more. It supports SpEL (Spring Expression Language) for complex expressions and can inject not just simple strings but also arrays, lists, and computed values. Best practices include using property placeholders for environment-specific configuration and avoiding hardcoded values. Common pitfalls involve forgetting to make the class a Spring bean or using @Value in static fields (which doesn't work). Real-world usage includes injecting database URLs, API keys, timeouts, and feature flags. Performance considerations are negligible as injection happens at bean creation time, but complex SpEL expressions should be cached if used frequently.

What is JpaRepository?

Quick Answer

Interface for generic CRUD operations on a repository for a specific type.

Detailed Explanation

JpaRepository provides high-level abstraction for JPA-based data access, offering CRUD operations, pagination, sorting, and query methods. Spring Data JPA generates implementations at runtime using proxies.

Internal Mechanics: Uses JDK dynamic proxies or bytecode enhancement to create repository implementations. Queries are generated from method names or annotations, executed via JPA Criteria API or JPQL.

Common Mistakes: Overusing @Query when derived methods suffice. Not handling Optional returns properly. Ignoring lazy loading issues.

Practical Use Cases: User management, product catalogs, audit logs. Any domain entity requiring persistence.

Performance Implications: N+1 query problem with lazy loading. Use fetch joins or entity graphs. Batch operations for bulk updates.

What is an Interceptor?

Quick Answer

Intercepts HTTP requests entering Spring MVC.

Detailed Explanation

HandlerInterceptor allows pre/post processing of HTTP requests in Spring MVC. Provides access to handler methods, model/view objects. Used for logging, authentication, caching.

Internal Mechanics: Part of HandlerExecutionChain. Executed in order: preHandle, postHandle, afterCompletion. Can short-circuit request processing.

Recommended Practices: Use for cross-cutting concerns. Keep logic lightweight. Implement conditionally.

Common Mistakes: Heavy processing in interceptors. Not handling exceptions properly. Assuming interceptor order.

Practical Use Cases: Request logging, authentication checks, performance monitoring, CORS handling.

Performance Implications: Executed for every request. Keep fast to avoid bottlenecks.

Code Example
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;
import org.springframework.stereotype.Component;
import org.springframework.web.context.request.WebRequestInterceptor;
import org.springframework.web.servlet.handler.WebRequestHandlerInterceptorAdapter;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Component
public class LoggingInterceptor implements HandlerInterceptor {
    private static final Logger logger = LoggerFactory.getLogger(LoggingInterceptor.class);
    private static final String START_TIME = "startTime";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // Executed before the controller method
        long startTime = System.currentTimeMillis();
        request.setAttribute(START_TIME, startTime);
        
        logger.info("Request started - Method: {}, URI: {}, Handler: {}", 
            request.getMethod(), 
            request.getRequestURI(), 
            handler.getClass().getSimpleName());
        
        // Return true to continue processing, false to stop
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler, ModelAndView modelAndView) throws Exception {
        // Executed after the controller method but before view rendering
        if (modelAndView != null) {
            logger.debug("View name: {}, Model keys: {}", 
                modelAndView.getViewName(), 
                modelAndView.getModel().keySet());
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        // Executed after the complete request processing (always called)
        long startTime = (Long) request.getAttribute(START_TIME);
        long duration = System.currentTimeMillis() - startTime;
        
        if (ex != null) {
            logger.error("Request failed - Method: {}, URI: {}, Duration: {}ms, Error: {}", 
                request.getMethod(), 
                request.getRequestURI(), 
                duration, 
                ex.getMessage());
        } else {
            logger.info("Request completed - Method: {}, URI: {}, Status: {}, Duration: {}ms", 
                request.getMethod(), 
                request.getRequestURI(), 
                response.getStatus(), 
                duration);
        }
    }
}

            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            response.getWriter().write("Missing or invalid authorization header");
            return false; // Stop processing
        }
        
        try {
            String token = authToken.substring(7); // Remove "Bearer "
            User user = userService.validateToken(token);
            request.setAttribute("currentUser", user);
            return true;
        } catch (Exception e) {
            logger.warn("Invalid token: {}", e.getMessage());
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            response.getWriter().write("Invalid token");
            return false;
        }
    }
}

What is dependency injection (DI) in Spring?

Quick Answer

DI is a design pattern where the objects that a class needs (dependencies) are passed to it ('injected') rather than the class creating them itself.

Detailed Explanation

Dependency Injection (DI) is a fundamental design pattern in Spring that promotes loose coupling and testability by inverting control of object creation. The Spring IoC (Inversion of Control) Container acts as a central registry that manages the lifecycle of beans, from instantiation to destruction. Internally, Spring uses reflection and proxying to inject dependencies at runtime. Constructor injection is preferred as it ensures immutability and makes dependencies explicit, reducing the risk of null pointer exceptions. Setter injection allows for optional dependencies and can be used for circular dependency resolution, while field injection (via @Autowired) is convenient but can make testing harder due to tight coupling. Best practices include favoring constructor injection for required dependencies and using @RequiredArgsConstructor from Lombok to reduce boilerplate. Common pitfalls include circular dependencies, which can cause application startup failures, and over-injection leading to bloated classes. In real-world scenarios, DI enables easier unit testing by allowing mock injection, supports modular architecture in microservices, and facilitates configuration changes without code modifications. Performance-wise, constructor injection has minimal overhead compared to setter injection, which may involve additional reflection calls.

What is Spring AOP?

Quick Answer

Aspect Oriented Programming.

Detailed Explanation

Spring AOP (Aspect-Oriented Programming) allows you to separate cross-cutting concerns like logging, transaction management, and security from your business logic. It works by creating proxies around your target objects and intercepting method calls to apply advice at specific join points. Internally, Spring uses either JDK dynamic proxies for interfaces or CGLIB proxies for classes. Pointcuts define where advice is applied, and advice types include @Before, @After, @Around, etc. Best practices include using AOP sparingly for truly cross-cutting concerns, keeping aspects focused, and avoiding complex pointcuts that are hard to maintain. Common pitfalls include performance overhead from proxying, circular dependencies, and unexpected behavior with final methods or private methods. In real-world scenarios, AOP is used for audit logging on service methods, caching results, or enforcing security checks. Performance considerations involve the proxy overhead; for high-performance applications, consider compile-time weaving with AspectJ.

An interface used to run specific code once the Spring Boot application has started.

Detailed Explanation

CommandLineRunner enables execution of initialization code after Spring context loading, useful for data seeding, cache warming, or startup validations. Internally, Spring Boot collects all CommandLineRunner beans and executes them in order (by @Order annotation or Ordered interface). ApplicationRunner provides similar functionality but with ApplicationArguments instead of raw strings. Best practices include keeping runners lightweight to avoid delaying startup, using @Order for execution sequencing, and handling exceptions gracefully. Common pitfalls include blocking startup with long-running operations and forgetting error handling. Real-world usage includes database migration verification, external service health checks, and loading reference data. Performance considerations involve asynchronous execution for non-critical startup tasks and monitoring execution time.

Code Example

import org.springframework.boot.CommandLineRunner;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Component
@Order(1) // Execute first
public class DatabaseSeeder implements CommandLineRunner {
private static final Logger logger = LoggerFactory.getLogger(DatabaseSeeder.class);

private final UserRepository userRepository;

public DatabaseSeeder(UserRepository userRepository) {
    this.userRepository = userRepository;
}

@Override
public void run(String... args) throws Exception {
    logger.info("Starting database seeding...");
    
    try {
        if (userRepository.count() == 0) {
            User admin = new User("admin", "admin@example.com", true);
            userRepository.save(admin);
            logger.info("Admin user created");
        } else {
            logger.info("Database already seeded");
        }
    } catch (Exception e) {
        logger.error("Failed to seed database", e);
        throw e; // Re-throw to prevent startup if critical
    }
}

}

What is the difference between @Configuration and @Component?

Quick Answer

@Configuration classes are proxied to ensure bean singleton semantics.

Detailed Explanation

While both can contain @Bean methods, @Configuration ensures that calling a @Bean method within the same class creates a singleton (it intercepts the call). @Component does not guarantee this interception (lite mode).

Code Example
@Configuration
public class AppConfig {
    @Bean
    public MyBean bean() { return new MyBean(); }
}

What is the difference between @Service, @Repository, and @Component?

Quick Answer

They are stereotypes for different layers, but all are Spring components.

Detailed Explanation

@Component is the generic stereotype. @Service annotates classes at the service layer. @Repository annotates classes at the persistence layer and adds automatic exception translation. Using specific annotations helps with clarity and AOP processing.

Code Example
@Service
public class MyService { ... }

@Repository
public class MyRepo { ... }

What is the difference between a Filter and an Interceptor?

Quick Answer

Filters belong to the Servlet container; Interceptors belong to the Spring context.

Detailed Explanation

Filters (Servlet API) intercept requests before they reach the DispatcherServlet. Interceptors (Spring MVC) intercept requests between the DispatcherServlet and the Controller. Interceptors have access to the handler and modelandview.

// Interceptor: checking user session or logging
