@Async return values?

Quick Answer

Void or Future.

Detailed Explanation

@Async runs methods in separate threads from a configured executor. Must return void, Future, or CompletableFuture. Internally, uses AOP and thread pools. Best practices: Configure custom executor; handle exceptions in caller. Common pitfalls: Void methods swallow exceptions; blocking on Future defeats purpose. In real-world usage, for email sending or heavy computations. Performance considerations: Thread pool sizing; monitor with Actuator.

Code Example
import org.springframework.scheduling.annotation.Async;
import org.springframework.scheduling.annotation.EnableAsync;
import org.springframework.stereotype.Service;
import java.util.concurrent.CompletableFuture;

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(5);
        executor.setQueueCapacity(10);
        executor.setThreadNamePrefix("MyAsync-");
        executor.initialize();
        return executor;
    }
}

@Service
public class AsyncService {

    @Async
    public CompletableFuture<String> asyncMethod() {
        return CompletableFuture.supplyAsync(() -> {
            try {
                // Simulate work
                Thread.sleep(1000);
                return "Result";
            } catch (Exception e) {
                throw new RuntimeException(e);
            }
        });
    }

    @Async
    public void asyncVoidMethod() {
        try {
            // Work
        } catch (Exception e) {
            // Log or handle
            log.error("Async error", e);
        }
    }
}

CompletableFuture<String> future = asyncService.asyncMethod();
future.thenAccept(result -> log.info("Got: {}", result));

@Cacheable mechanism?

Quick Answer

Proxy intercepts call and checks cache.

Detailed Explanation

@Cacheable uses AOP proxies to intercept method calls. The proxy checks the cache first; if found, returns cached value without executing the method. If not, executes the method and caches the result. Spring supports multiple cache managers (Caffeine, Redis, EhCache). Keys are generated from method parameters by default. Internally, uses ConcurrentHashMap for local caching. Best practices include meaningful key generation, cache eviction strategies, and monitoring. Common pitfalls include caching inappropriate data or ignoring cache invalidation. Real-world scenarios include expensive computations or database queries. Performance considerations: caching reduces computation time but adds memory/serialization overhead.

Code Example
import org.springframework.cache.annotation.Cacheable;
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.CachePut;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.stereotype.Service;

@Configuration
@EnableCaching
public class CacheConfig {
    
    @Bean
    public CacheManager cacheManager() {
        CaffeineCacheManager cacheManager = new CaffeineCacheManager();
        cacheManager.setCaffeine(Caffeine.newBuilder()
            .maximumSize(1000)
            .expireAfterWrite(10, TimeUnit.MINUTES)
            .recordStats());
        return cacheManager;
    }
}

@ConfigurationProperties vs @Value?

Quick Answer

Type-safe bulk configuration vs single-value injection.

Detailed Explanation

@ConfigurationProperties provides type-safe binding of external configuration to POJOs with validation and nested property support, while @Value is suitable for simple string-based property injection. Internally, @ConfigurationProperties uses property converters and validators for robust configuration handling. Best practices include using @Validated for validation, providing default values, and structuring properties hierarchically. Common pitfalls include forgetting to add getters/setters, misconfigured property prefixes, and validation errors causing startup failures. Real-world usage includes complex application settings, database configurations, and feature flags. Performance considerations involve caching resolved properties and minimizing property access in hot paths.

Detailed Explanation

@Primary marks a bean as default when multiple candidates exist. @Qualifier specifies exact bean by name or custom qualifier. @Primary is class-level, @Qualifier is injection-point level. BeanPostProcessor vs BeanFactoryPostProcessor?

Quick Answer

Instance modification vs Definition modification.

Detailed Explanation

BeanPostProcessor (BPP) and BeanFactoryPostProcessor (BFPP) serve different purposes in Spring's bean lifecycle. BFPP operates on bean definitions (BeanDefinition objects) before any beans are instantiated, allowing modifications to metadata like property values, constructor arguments, or bean scopes. It's commonly used for property placeholder resolution (${...}) and profile-based bean registration. BPP, on the other hand, works on actual bean instances after instantiation but before/after initialization, enabling instance-level modifications like dependency injection or proxy creation. BFPPs are executed once during context startup, while BPPs are called for every bean creation. Best practices include using BFPP for configuration processing and BPP for runtime behavior modification. Common pitfalls include trying to access bean instances in BFPP (which aren't created yet) or performing heavy operations in BPP. Real-world usage includes custom property sources in BFPP and AOP proxy injection in BPP. Performance considerations: BFPP runs once at startup, so complex logic is acceptable; BPP should be lightweight as it's called per bean.

Code Example
import org.springframework.beans.factory.config.BeanFactoryPostProcessor;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;

@Component
public class CustomBeanFactoryPostProcessor implements BeanFactoryPostProcessor {
    
    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory) {
        // Modify bean definitions before instantiation
        for (String beanName : beanFactory.getBeanDefinitionNames()) {
            BeanDefinition bd = beanFactory.getBeanDefinition(beanName);
            if (bd.getBeanClassName() != null && bd.getBeanClassName().contains("Service")) {
                bd.setScope("prototype"); // Change scope
            }
        }
    }
}

@Component
public class CustomBeanPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean instanceof MyService) {
            // Wrap bean instance with monitoring proxy
            return new MonitoredService((MyService) bean);
        }
        return bean;
    }
}

// Usage in configuration
@Configuration
public class AppConfig {
    
    @Bean
    public MyService myService() {
        return new MyServiceImpl();
    }
}

AuthenticationManager vs Provider?

Quick Answer

Manager delegates to Providers.

Detailed Explanation

In Spring Security, AuthenticationManager is the entry point for authentication requests, typically implemented by ProviderManager. It delegates to a list of AuthenticationProviders, each handling specific authentication mechanisms (DAO, LDAP, JWT, OAuth). The manager iterates through providers until one successfully authenticates or all fail. Providers implement the authenticate() method, checking credentials and returning an Authentication object with granted authorities. This design allows multiple authentication strategies in one application. Best practices include ordering providers by specificity and using custom providers for proprietary systems. Common pitfalls include providers throwing exceptions instead of returning null, or misconfigured provider chains. Real-world scenarios include enterprise apps with LDAP + database fallback, or microservices with JWT validation. Performance considerations: providers should be fast to avoid authentication bottlenecks; consider caching successful authentications.

Code Example
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.AuthenticationProvider;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.AuthenticationException;
import org.springframework.stereotype.Component;

@Component
public class CustomAuthenticationProvider implements AuthenticationProvider {
    
    @Override
    public Authentication authenticate(Authentication authentication) throws AuthenticationException {
        String username = authentication.getName();
        String password = authentication.getCredentials().toString();
        
        // Custom authentication logic
        User user = userService.findByUsername(username);
        if (user != null && passwordEncoder.matches(password, user.getPassword())) {
            return new UsernamePasswordAuthenticationToken(
                user, password, user.getAuthorities()
            );
        }
        
        throw new BadCredentialsException("Invalid credentials");
    }
    
    @Override
    public boolean supports(Class<?> authentication) {
        return UsernamePasswordAuthenticationToken.class.isAssignableFrom(authentication);
    }
}

@Configuration
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    
    @Autowired
    private CustomAuthenticationProvider customProvider;
    
    @Override
    protected void configure(AuthenticationManagerBuilder auth) {
        auth.authenticationProvider(customProvider);
    }
    
    @Bean
    @Override
    public AuthenticationManager authenticationManagerBean() throws Exception {
        return super.authenticationManagerBean();
    }
}

Bean Lifecycle?

Quick Answer

Instantiate -> Populate -> Init -> Destruction.

Detailed Explanation

The Spring bean lifecycle involves several phases: instantiation (creating the bean instance), property population (injecting dependencies), initialization (calling init methods), and destruction (cleanup). Internally, BeanPostProcessors intercept at pre-init and post-init stages, while aware interfaces like BeanNameAware allow beans to know their names. Best practices: Use @PostConstruct for initialization and @PreDestroy for cleanup; implement InitializingBean/DisposableBean sparingly. Common pitfalls: Forgetting to release resources in destroy phase, leading to memory leaks, or performing heavy operations in init. In real-world usage, custom beans like connection pools need proper lifecycle management. Performance considerations: Initialization can delay startup; use lazy beans for heavy init. Monitor with Actuator's bean endpoints.

Circular Dependencies?

Quick Answer

Bean A needs B, B needs A.

Detailed Explanation

Circular dependencies occur when beans depend on each other. Spring resolves for singletons using a three-level cache with early bean references (proxies). Fails for constructor injection; use @Lazy or setter injection. Best practices: Redesign to avoid cycles; use @Lazy for constructors. Common pitfalls: Constructor cycles cause BeanCreationException; proxies add overhead. In real-world usage, common in service layers; refactor with events or interfaces. Performance considerations: Proxy resolution adds startup time; monitor bean creation.

Code Example
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
public class ServiceA {

    private final ServiceB serviceB;

    @Lazy  // Use @Lazy to break cycle
    public ServiceA(ServiceB serviceB) {
        this.serviceB = serviceB;
    }

    public void methodA() {
        serviceB.methodB();
    }
}

@Service
public class ServiceB {

    private final ServiceA serviceA;

    @Lazy
    public ServiceB(ServiceA serviceA) {
        this.serviceA = serviceA;
    }

    public void methodB() {
        // Business logic
    }
}

// Alternative: Setter injection
@Service
public class ServiceA {
    private ServiceB serviceB;

    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}

Configure Spring Boot as OAuth2 Resource Server.

Quick Answer

Validates JWT tokens issued by an Authorization Server (like Keycloak/Auth0).

Detailed Explanation

As an OAuth2 Resource Server, Spring Boot validates JWT tokens by fetching public keys from the authorization server's JWKS endpoint. Internally, it uses Spring Security's JwtDecoder to verify token signatures, check expiration, and extract claims. The issuer URI is crucial as it tells Spring where to find the JWKS endpoint.

Best practices include validating the audience claim, using HTTPS for token endpoints, and implementing proper error handling for invalid tokens. Common pitfalls involve misconfigured issuer URIs leading to validation failures, or not handling token expiration gracefully. Real-world usage scenarios include securing REST APIs in microservices, where tokens are issued by a central auth server. Performance considerations: JWKS keys are cached by default; consider custom caching strategies for high-traffic applications and monitor token validation latency.

import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.jwt.JwtDecoder;
import org.springframework.security.oauth2.jwt.JwtValidators;

            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()

    return decoder;
}

import org.springframework.security.oauth2.core.OAuth2Error;
import org.springframework.security.oauth2.core.OAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidatorResult;
import org.springframework.security.oauth2.jwt.Jwt;

import java.util.List;

public class AudienceValidator implements OAuth2TokenValidator {
private final List allowedAudiences;

public AudienceValidator(List<String> allowedAudiences) {
    this.allowedAudiences = allowedAudiences;
}

@Override
public OAuth2TokenValidatorResult validate(Jwt jwt) {
    List<String> audiences = jwt.getAudience();
    if (audiences == null || audiences.isEmpty()) {
        return OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Missing audience claim", null));
    }
    for (String audience : audiences) {
        if (allowedAudiences.contains(audience)) {
            return OAuth2TokenValidatorResult.success();
        }
    }
    return OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Invalid audience", null));
}

}

Custom BeanPostProcessor implementation.

Quick Answer

Hooking into the bean lifecycle to modify beans before/after initialization.

Detailed Explanation

BeanPostProcessors intercept bean creation, allowing modification or wrapping. Internally, Spring calls postProcessBeforeInitialization and postProcessAfterInitialization during bean lifecycle. This enables AOP proxying, property injection, and validation.

Best practices include checking bean types before processing, using conditional logic, and avoiding side effects. Common pitfalls involve modifying beans unexpectedly or causing circular dependencies. Real-world usage scenarios include custom annotations, security proxies, and monitoring wrappers. Performance considerations: Processors run for every bean; keep them lightweight and use caching.

public class MonitoringInterceptor implements MethodInterceptor {

private final Map<String, Integer> callCounts = new HashMap<>();

@Override
public Object invoke(MethodInvocation invocation) throws Throwable {
    String methodName = invocation.getMethod().getName();
    callCounts.merge(methodName, 1, Integer::sum);
    
    long start = System.nanoTime();
    try {
        return invocation.proceed();

    }
}

DataMulti-Tenancy

Database Multi-Tenancy strategies.

Quick Answer

Serving multiple clients (tenants) from one app instance.

// Repository interface
@Repository
public interface UserRepository extends JpaRepository<User, Long>, JpaSpecificationExecutor {
// JpaSpecificationExecutor provides methods like findAll(Specification)
}

// Specification class
public class UserSpecifications {

public static Specification<User> hasName(String name) {
    return (root, query, criteriaBuilder) -> {
        if (name == null || name.isEmpty()) {
            return criteriaBuilder.conjunction(); // Always true
        }
        return criteriaBuilder.like(criteriaBuilder.lower(root.get("name")), "%" + name.toLowerCase() + "%");
    };
}

public static Specification<User> hasAgeGreaterThan(Integer age) {
    return (root, query, criteriaBuilder) -> {
        if (age == null) {
            return criteriaBuilder.conjunction();
        }
        return criteriaBuilder.greaterThan(root.get("age"), age);
    };
}

public static Specification<User> isActive(Boolean active) {
    return (root, query, criteriaBuilder) -> {
        if (active == null) {
            return criteriaBuilder.conjunction();
        }
        return criteriaBuilder.equal(root.get("active"), active);
    };
}

// Combined specification
public static Specification<User> searchUsers(String name, Integer minAge, Boolean active) {
    return Specification.where(hasName(name))
        .and(hasAgeGreaterThan(minAge))
        .and(isActive(active));
}

}

How do Application Events work in Spring?

Quick Answer

A mechanism for decoupled communication between beans.

Detailed Explanation

Spring Application Events provide a decoupled communication mechanism between application components, allowing beans to publish and listen to events without direct dependencies. Events extend ApplicationEvent (or use PayloadApplicationEvent for simple payloads), and publishers use ApplicationEventPublisher (injected or accessed via ApplicationContext). Listeners implement ApplicationListener<T> or use @EventListener annotation. Internally, the framework uses ApplicationEventMulticaster (default SimpleApplicationEventMulticaster) to manage synchronous or asynchronous event publishing, with support for ordered listeners via @Order. Events can be synchronous (blocking) or asynchronous using @Async or ApplicationEventMulticaster configuration. Best practices include making events immutable, using specific event types for different scenarios, and handling exceptions in listeners to prevent blocking other listeners. Use @TransactionalEventListener for events that should be published after transaction commit. Common pitfalls include tight coupling if events are overused for simple method calls, event loss in asynchronous scenarios without proper error handling, or memory leaks from accumulating unprocessed events. In real-world scenarios, events are ideal for cross-cutting concerns like user registration notifications, cache invalidation, audit logging, and system monitoring. For distributed systems, events can trigger actions across microservices. Performance considerations show synchronous events have minimal overhead but can block publishers; asynchronous events use thread pools but risk event loss if not configured properly. Monitor event processing with custom metrics and use EventPublishingRunListener for application lifecycle events.

How do you create a custom Spring Boot Starter?

Quick Answer

Create an auto-configure module and a starter module.

Detailed Explanation

Creating a custom Spring Boot Starter involves architecting two interdependent Maven modules: an auto-configuration module containing the conditional bean registration logic, and a starter module that serves as a dependency aggregator, pulling in the auto-configuration along with all necessary third-party libraries. The auto-configuration module houses classes annotated with @AutoConfiguration (or @Configuration with @Conditional annotations), which leverage Spring's condition framework to register beans only when appropriate dependencies and conditions are met. These classes must be declared in META-INF/spring.factories for Spring Boot versions before 2.7, or in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports for 2.7 and later, ensuring the framework discovers and processes them during startup. Internally, starters exploit Maven's transitive dependency resolution, automatically including compatible versions of libraries to prevent version conflicts, while the auto-configuration uses annotations like @ConditionalOnClass, @ConditionalOnMissingBean, and @ConditionalOnProperty to make decisions at runtime. The naming convention *-starter (e.g., my-library-starter) signals to developers that it's a Spring Boot starter. Best practices include making starters opinionated yet configurable through properties, providing sensible defaults, documenting all configuration options, and including integration tests using @SpringBootTest to verify auto-configuration works correctly. Common pitfalls include creating circular dependencies between starters, failing to handle optional dependencies gracefully (leading to NoClassDefFoundError), or shipping starters with hardcoded versions that conflict with user applications. In real-world usage, custom starters excel at encapsulating common configurations across microservices, such as a custom security starter that configures OAuth2 and JWT validation, or a data starter that sets up connection pooling and migrations. They promote code reuse and consistency in enterprise environments. Performance considerations are primarily build-time: starters should minimize the number of transitive dependencies to avoid bloating the classpath and increasing build times. At runtime, ensure auto-configurations are lightweight and don't perform expensive operations during bean creation. For testing, create a separate test module that includes the starter and verifies behavior under different conditions. When publishing, deploy to Maven repositories like Nexus or Artifactory, and consider using Spring Boot's starter validation tools to ensure compatibility across versions.

How does the Spring Security filter chain work?

Quick Answer

It is a chain of Servlet filters that intercept requests for authentication and authorization.

Detailed Explanation

The Spring Security filter chain is a sophisticated, ordered sequence of Servlet filters that intercept HTTP requests to enforce authentication, authorization, and other security policies, forming the backbone of Spring Security's architecture. It begins with a DelegatingFilterProxy registered in the web.xml or via Java configuration, which delegates to a FilterChainProxy managed by Spring. This proxy orchestrates multiple SecurityFilterChain instances, each matching specific URL patterns through RequestMatcher implementations (like AntPathRequestMatcher or RegexRequestMatcher). Each chain contains a series of filters with defined order, including SecurityContextPersistenceFilter (manages SecurityContext), UsernamePasswordAuthenticationFilter (handles form login), BasicAuthenticationFilter (HTTP Basic auth), CsrfFilter (prevents CSRF attacks), ExceptionTranslationFilter (handles security exceptions), and others. Filters can authenticate users by extracting credentials, authorize access based on roles/permissions, modify requests/responses, or short-circuit the chain. Internally, the chain uses a SecurityContextHolder (with strategies like MODE_THREADLOCAL for storing authentication details) and AuthenticationManager for credential verification, which delegates to ProviderManager and various AuthenticationProviders (e.g., DaoAuthenticationProvider for database auth). The framework supports multiple authentication mechanisms and can be extended with custom filters. Best practices include customizing filter order using @Order on filter beans, leveraging method security with @PreAuthorize, @PostAuthorize, and @Secured annotations (processed by MethodSecurityInterceptor), enabling CSRF protection for state-changing operations, and using @EnableGlobalMethodSecurity for comprehensive security. Implement role-based access control (RBAC) or attribute-based access control (ABAC) as needed. Common pitfalls include misconfigured filter orders causing security bypasses (e.g., placing authorization before authentication), forgetting to secure actuator endpoints (use management.security.enabled=true in older versions), mixing authentication mechanisms incorrectly, or exposing sensitive information in error messages. In real-world scenarios, the filter chain protects REST APIs with JWT tokens (using JwtAuthenticationFilter), secures microservices with OAuth2/OIDC (via OAuth2LoginAuthenticationFilter), and implements single sign-on (SSO) solutions. For high-traffic applications, consider session management strategies: use stateless JWT for APIs to avoid server-side sessions, or configure distributed sessions with Redis for stateful apps. Performance considerations involve minimizing filter processing time; cache authentication results, use asynchronous authentication for external providers, and monitor with Spring Boot Actuator's security metrics. For debugging, enable DEBUG logging on org.springframework.security to trace filter execution. Integration with Spring WebFlux uses a reactive equivalent with ServerHttpSecurity for non-blocking security.

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Component;
import java.util.Date;
import java.util.function.Function;

@Component
public class JwtUtil {
    private final String SECRET_KEY = "your-secret-key"; // In production, use environment variable
    
    public String generateToken(Authentication authentication) {
        UserDetails userDetails = (UserDetails) authentication.getPrincipal();
        return Jwts.builder()
            .setSubject(userDetails.getUsername())
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + 86400000)) // 24 hours
            .signWith(SignatureAlgorithm.HS256, SECRET_KEY)
            .compact();
    }
    
    public String extractUsername(String token) {
        return extractClaim(token, Claims::getSubject);
    }
    
    public <T> T extractClaim(String token, Function<Claims, T> claimsResolver) {
        final Claims claims = extractAllClaims(token);
        return claimsResolver.apply(claims);
    }
    
    private Claims extractAllClaims(String token) {
        return Jwts.parser().setSigningKey(SECRET_KEY).parseClaimsJws(token).getBody();
    }
    
    public boolean isTokenExpired(String token) {
        return extractExpiration(token).before(new Date());
    }
    
    private Date extractExpiration(String token) {
        return extractClaim(token, Claims::getExpiration);
    }
    
    public boolean validateToken(String token, UserDetails userDetails) {
        final String username = extractUsername(token);
        return (username.equals(userDetails.getUsername()) && !isTokenExpired(token));
    }
}

public class JwtAuthenticationFilter extends OncePerRequestFilter {
    
    @Autowired

            throws ServletException, IOException {

        String username = null;
        String jwt = null;
        
        if (authorizationHeader != null && authorizationHeader.startsWith("Bearer ")) {
            jwt = authorizationHeader.substring(7);

            }

            UserDetails userDetails = userDetailsService.loadUserByUsername(username);
            if (jwtUtil.validateToken(jwt, userDetails)) {
                UsernamePasswordAuthenticationToken authToken =

                authToken.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContextHolder.getContext().setAuthentication(authToken);
            }
        }
        chain.doFilter(request, response);
    }

Isolation Levels?

Quick Answer

Manage visibility of changes between concurrent transactions.

Detailed Explanation

Isolation levels control how transaction changes are visible to others. READ_UNCOMMITTED allows dirty reads (seeing uncommitted changes). READ_COMMITTED (default) prevents dirty reads but allows non-repeatable reads. REPEATABLE_READ prevents both but allows phantom reads. SERIALIZABLE prevents all anomalies by serializing transactions. Higher levels use more locking, reducing performance. Internally, databases implement via locking or MVCC. Best practices match level to consistency needs; use READ_COMMITTED for most apps. Common pitfalls include SERIALIZABLE causing deadlocks or performance issues. Real-world scenarios include financial systems needing SERIALIZABLE vs. analytics accepting READ_COMMITTED. Performance considerations: higher isolation increases lock contention and reduces throughput.

Code Example
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AccountService {
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void transferMoney(Account from, Account to, BigDecimal amount) {
        // Default level - prevents dirty reads
        BigDecimal fromBalance = from.getBalance();
        if (fromBalance.compareTo(amount) < 0) {
            throw new InsufficientFundsException();
        }
        
        from.setBalance(fromBalance.subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
    }
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public Account getAccountForUpdate(Long id) {
        // Ensures consistent reads during transaction
        return accountRepository.findById(id)
            .orElseThrow(() -> new AccountNotFoundException(id));
    }
}

@Repository
public interface AccountRepository extends JpaRepository<Account, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);
}

Mono vs Flux?

Quick Answer

0-1 items vs 0-N items.

Detailed Explanation

Mono and Flux are Project Reactor types for reactive programming in Spring WebFlux. Mono represents a Publisher that emits 0 or 1 item, similar to Optional or Future. Flux emits 0 to N items, like a Stream. Both support backpressure and are lazy - nothing happens until subscribed. Internally, they use operators for transformation, filtering, and composition. Mono is used for single-value responses (e.g., findById), Flux for collections (e.g., findAll). Best practices include proper error handling with onErrorResume, avoiding blocking operations, and using Schedulers for threading. Common pitfalls include forgetting to subscribe, causing memory leaks, or mixing blocking/non-blocking code. Real-world scenarios include streaming large datasets, handling external API calls, or implementing chat applications. Performance considerations: reactive code can handle more concurrent connections with fewer threads, but operators add overhead; profile for bottlenecks.

Code Example
import reactor.core.publisher.Mono;
import reactor.core.publisher.Flux;
import org.springframework.web.bind.annotation.*;

@RestController
public class ReactiveController {
    
    @Autowired
    private UserRepository userRepository;
    
    // Mono for single item
    @GetMapping("/user/{id}")
    public Mono<User> getUser(@PathVariable String id) {
        return userRepository.findById(id)
            .switchIfEmpty(Mono.error(new UserNotFoundException("User not found")))
            .doOnNext(user -> log.info("Found user: " + user.getName()));
    }
    
    // Flux for multiple items
    @GetMapping("/users")
    public Flux<User> getAllUsers() {
        return userRepository.findAll()
            .filter(user -> user.isActive())
            .map(this::enrichUser)
            .onErrorResume(e -> {
                log.error("Error fetching users", e);
                return Flux.empty();
            });
    }
    
    // Combining Mono and Flux
    @GetMapping("/user/{id}/posts")
    public Mono<UserWithPosts> getUserWithPosts(@PathVariable String id) {
        Mono<User> userMono = userRepository.findById(id);
        Flux<Post> postsFlux = postRepository.findByUserId(id);
        
        return Mono.zip(userMono, postsFlux.collectList())
            .map(tuple -> new UserWithPosts(tuple.getT1(), tuple.getT2()));
    }
    
    // Error handling
    @PostMapping("/user")
    public Mono<User> createUser(@RequestBody User user) {
        return userRepository.save(user)
            .onErrorMap(ConstraintViolationException.class, 
                e -> new BadRequestException("Invalid user data"))
            .doOnSuccess(savedUser -> log.info("Created user: " + savedUser.getId()));
    }
    
    private User enrichUser(User user) {
        // Add additional data
        user.setDisplayName(user.getFirstName() + " " + user.getLastName());
        return user;
    }
}

Quick Answer

Detailed Explanation

Transaction propagation defines how transactions interact: REQUIRED joins existing or creates new; REQUIRES_NEW suspends current and starts new; NESTED creates savepoint in existing. Internally, managed by PlatformTransactionManager. Best practices: Use REQUIRED for most cases; REQUIRES_NEW for independent operations. Common pitfalls: REQUIRES_NEW can cause data inconsistency if outer fails; NESTED not supported by all databases. In real-world scenarios, critical for banking where operations must be atomic. Performance considerations: REQUIRES_NEW adds overhead; monitor with transaction metrics.

Code Example
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.annotation.Propagation;

@Service
public class TransactionService {

    @Transactional(propagation = Propagation.REQUIRED)
    public void requiredMethod() {
        // Joins existing transaction or creates new
        doWork();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void requiresNewMethod() {
        // Suspends current, creates new
        doIndependentWork();
    }

    @Transactional(propagation = Propagation.NESTED)
    public void nestedMethod() {
        // Creates savepoint in existing
        doNestedWork();
    }

    private void doWork() {
        try {
            // Business logic
            repository.save(entity);
        } catch (Exception e) {
            throw new RuntimeException("Transaction failed", e);
        }
    }
}

REQUIRED vs REQUIRES_NEW propagation?

Quick Answer

Join existing vs Create new (suspend existing).

Detailed Explanation

Transaction propagation defines how transactions interact. REQUIRED (default) joins an existing transaction or creates one if none exists. REQUIRES_NEW always creates a new transaction, suspending any current one. If the inner transaction fails, the outer can still commit if the exception is caught. Internally, Spring uses ThreadLocal to track transactions and suspends by saving transaction context. Best practices include using REQUIRES_NEW for audit logging or external calls that must succeed independently. Common pitfalls include unhandled exceptions in REQUIRES_NEW causing inconsistent states or performance overhead from nested transactions. Real-world scenarios include payment processing where confirmation emails are sent in separate transactions. Performance considerations: REQUIRES_NEW adds overhead; use sparingly and ensure proper exception handling.

Code Example
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    
    @Autowired
    private PaymentService paymentService;
    
    @Autowired
    private AuditService auditService;
    
    @Transactional(propagation = Propagation.REQUIRED)
    public void processOrder(Order order) {
        // This method will join existing transaction or create new
        validateOrder(order);
        saveOrder(order);
        
        try {
            paymentService.processPayment(order);
        } catch (PaymentException e) {
            // Payment failed, but audit should still happen
            throw e;
        }
        
        // Audit in separate transaction - will succeed even if order fails
        auditService.logOrder(order);
    }
}

@Service
public class PaymentService {
    
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processPayment(Order order) {
        // This runs in a new transaction
        // Even if outer transaction rolls back, payment is committed
        debitAccount(order);
        creditMerchant(order);
        
        if (someCondition) {
            throw new PaymentException("Payment failed");
        }
    }
}

@Service
public class AuditService {
    
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logOrder(Order order) {
        // Always commits, even if order processing fails
        auditRepository.save(new AuditEntry("ORDER_PROCESSED", order.getId()));
    }
}

Solving N+1 Problem in Hibernate/JPA.

Quick Answer

The N+1 problem occurs when fetching N entities entails 1 query for the list and N additional queries for related entities.

Detailed Explanation

The N+1 problem arises in ORM frameworks like Hibernate when lazy loading is used, causing additional queries for each related entity. Internally, when you fetch a list of entities, Hibernate loads only the main entities initially, then fires separate queries for each associated entity when accessed. This can lead to hundreds of queries for large datasets.

Best practices include using eager fetching judiciously with JOIN FETCH or @EntityGraph, preferring lazy loading by default and fetching associations only when needed, and using batch fetching with @BatchSize for collections. Common pitfalls involve over-eager fetching causing Cartesian products or fetching unnecessary data, or forgetting to optimize queries in production. Real-world usage scenarios include listing pages with related data, like displaying users with their roles or orders with items. Performance considerations: JOIN FETCH can result in duplicate data in result sets; use DISTINCT in JPQL or Set in Java to handle this. Monitor query execution with tools like Hibernate's SQL logging or JPA's query hints. For complex cases, consider using DTO projections or native queries.

What is @ConditionalOnProperty?

Quick Answer

A condition that matches only if a specific property is set in the environment.

Detailed Explanation

@ConditionalOnProperty is a powerful Spring Boot condition annotation that enables or disables bean registration based on the presence, absence, or value of properties in the environment (application.properties, environment variables, etc.). It works by checking the Environment abstraction, supporting parameters like name (property key), havingValue (expected value for match), matchIfMissing (behavior when property is absent, defaults to false), and prefix (for grouped properties). Internally, it integrates with Spring's condition evaluation framework, using ConditionContext to access the environment and registered beans. This allows for dynamic configuration where features can be toggled without code changes. Best practices include using descriptive property names (e.g., features.x.enabled), providing sensible defaults with matchIfMissing = true, documenting all properties in configuration metadata, and combining with other conditions for complex logic. Use @ConditionalOnExpression for more advanced conditions. Common pitfalls include typos in property names leading to unexpected behavior, forgetting that properties are case-sensitive, or assuming properties are always strings (they can be converted to other types). In real-world scenarios, @ConditionalOnProperty is essential for feature toggles in continuous deployment, enabling/disabling modules like caching, security features, or third-party integrations based on environment (dev/staging/prod). For microservices, it allows conditional registration of beans based on service roles or deployment configurations. Performance considerations are minimal since evaluation happens at application startup, but avoid expensive operations in condition classes. For debugging, enable condition evaluation logging with logging.level.org.springframework.context.annotation.ConditionEvaluator=DEBUG to see why conditions match or fail. It works seamlessly with profiles (@Profile) and other conditional annotations, allowing fine-grained control over application composition.

What is BeanPostProcessor?

Quick Answer

Interface to modify beans before/after initialization.

Detailed Explanation

BeanPostProcessor is a Spring framework interface that allows customization of bean instances during their lifecycle. It provides two methods: postProcessBeforeInitialization and postProcessAfterInitialization, which are called before and after the bean's initialization methods (@PostConstruct, InitializingBean.afterPropertiesSet, or custom init-method). Spring uses BPPs internally for AOP proxy creation, @Autowired processing, @Value injection, and validation. The interface is particularly powerful because it operates on bean instances, allowing modifications like wrapping with proxies or injecting dependencies. BPPs are registered automatically if they implement the interface and are managed by Spring. Best practices include implementing Ordered or PriorityOrdered for execution order control and being thread-safe since they may be called concurrently. Common pitfalls include modifying beans in ways that break contracts or causing circular dependencies. Real-world scenarios include custom annotation processing, security proxy injection, or metrics collection. Performance considerations involve keeping processing lightweight since it's called for every bean, and avoiding expensive operations in these methods.

Code Example
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;

@Component
public class CustomBeanPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if (bean instanceof MyService) {
            System.out.println("Before initialization: " + beanName);
            // Perform pre-initialization logic
        }
        return bean;
    }
    
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean instanceof MyService) {
            System.out.println("After initialization: " + beanName);
            // Wrap with proxy for additional behavior
            return createProxy(bean);
        }
        return bean;
    }
    
    private Object createProxy(Object target) {
        // Use dynamic proxy or CGLIB to wrap the bean
        return Proxy.newProxyInstance(
            target.getClass().getClassLoader(),
            target.getClass().getInterfaces(),
            (proxy, method, args) -> {
                System.out.println("Method " + method.getName() + " called");
                try {
                    return method.invoke(target, args);
                } catch (Exception e) {
                    throw new RuntimeException(e);
                }
            }
        );
    }
}

What is a generic @SpringBootTest vs a Slice Test?

Quick Answer

@SpringBootTest loads the full context; Slice tests (like @WebMvcTest) load only a specific layer.

Detailed Explanation

@SpringBootTest is a comprehensive integration test annotation that loads the entire Spring application context, including all beans, auto-configurations, and external dependencies, making it ideal for end-to-end testing but slow due to full context initialization. In contrast, slice tests like @WebMvcTest, @DataJpaTest, @RestClientTest, and @JsonTest load only a subset of the context relevant to a specific layer (web layer, data layer, etc.), providing faster, more focused unit-like tests by using @ImportAutoConfiguration selectively. Internally, @SpringBootTest uses SpringApplication to bootstrap the context, while slice tests employ ApplicationContextRunner or specific test slices that register only necessary components. Best practices include using slice tests for most scenarios to improve test speed and isolation, reserving full @SpringBootTest for integration tests requiring the complete application. Configure test properties with @TestPropertySource and use @MockBean or @SpyBean for mocking dependencies. Common pitfalls include overusing @SpringBootTest leading to slow test suites, forgetting to configure test-specific properties, or testing implementation details instead of behavior. In real-world scenarios, @WebMvcTest validates controller logic and HTTP responses, @DataJpaTest tests repository operations with an embedded database, and full integration tests verify service interactions. Performance considerations show slice tests run 5-10x faster than full context tests; for large applications, parallel test execution and selective context caching can help. Use @DirtiesContext sparingly as it forces context recreation. For reactive applications, @WebFluxTest provides similar slicing for WebFlux controllers.

Quick Answer

Detailed Explanation

Common pitfalls include overusing AOP leading to complex debugging, forgetting that advice doesn't apply to self-invocations within the same class, and performance degradation from excessive pointcut matching. Real-world usage includes implementing audit trails, security checks, and performance monitoring across multiple services. Performance considerations involve minimizing the number of pointcuts and using caching for expensive advice logic.

What is Aspect-Oriented Programming (AOP) in Spring?

Quick Answer

A way to modularize cross-cutting concerns like logging or transaction management.

Detailed Explanation

Aspect-Oriented Programming (AOP) in Spring provides a powerful mechanism for modularizing cross-cutting concerns—behaviors that span multiple classes and would otherwise lead to code duplication and tight coupling, such as logging, security, caching, and transaction management. It achieves this through aspects (classes containing advice), which are applied to join points (specific points in program execution, like method calls) via pointcuts (expressions defining where advice should execute). Spring AOP employs proxy-based interception: JDK dynamic proxies for interfaces and CGLIB proxies for classes, creating proxy objects that intercept method calls and execute advice before, after, or around the original method. Advice types include @Before (executes before join point), @After (executes after, regardless of outcome), @Around (wraps the join point, controlling execution), @AfterReturning (executes after successful return), and @AfterThrowing (executes after exception). Pointcuts use expressions like execution(* com.example.service.*.*(..)) to match methods. Internally, AOP uses AspectJ weaving at runtime, with Spring managing proxy creation and advice application through ProxyFactory and AdvisedSupport. Best practices include using pointcuts judiciously to avoid performance overhead (each proxy adds indirection), combining AOP with @Transactional for declarative transactions, and ensuring aspects are singleton-scoped. Use @Order to control aspect precedence when multiple aspects apply to the same join point. Common pitfalls include self-invocation bypassing proxies (solve with @Autowired or AopContext.currentProxy()), overusing AOP leading to complex debugging (use logging aspects sparingly), forgetting proxy limitations (e.g., final methods can't be advised), or creating circular dependencies between aspects and target objects. In real-world scenarios, AOP excels at implementing auditing (logging all method calls to sensitive services), performance monitoring (timing method execution), security enforcement (checking permissions before method calls), and caching (intercepting getter methods). For distributed systems, it can implement circuit breakers or retry logic. Performance considerations are critical: simple advice like @Before has minimal overhead (nanoseconds), but @Around can add latency due to method interception; monitor with profiling tools. For high-throughput applications, consider compile-time weaving with AspectJ instead of runtime proxies. Debugging AOP involves enabling DEBUG logging on org.springframework.aop and using ProxyFactoryBean for manual proxy creation in tests. Integration with Spring Boot auto-configures AOP with @EnableAspectJAutoProxy, and it works seamlessly with reactive programming in WebFlux.

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.*;
import org.aspectj.lang.reflect.MethodSignature;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;

@Aspect
@Component
@Order(1) // Higher precedence
public class LoggingAspect {
    
    @Pointcut("execution(* com.example.service.*.*(..))")
    public void serviceMethods() {}
    
    @Pointcut("execution(* com.example.repository.*.*(..))")
    public void repositoryMethods() {}
    
    @Pointcut("serviceMethods() || repositoryMethods()")
    public void dataLayer() {}
    
    @Before("dataLayer()")
    public void logBefore() {
        System.out.println("Method execution started at " + System.currentTimeMillis());
    }
    
    @AfterReturning(pointcut = "dataLayer()", returning = "result")
    public void logAfterReturning(Object result) {
        System.out.println("Method returned: " + (result != null ? result.toString() : "null"));
    }
    
    @AfterThrowing(pointcut = "dataLayer()", throwing = "ex")
    public void logAfterThrowing(Exception ex) {
        System.err.println("Exception thrown: " + ex.getClass().getSimpleName() + " - " + ex.getMessage());
    }
    
    @After("dataLayer()")
    public void logAfter() {
        System.out.println("Method execution finished");
    }
    
    @Around("dataLayer()")
    public Object logAround(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        String methodName = joinPoint.getSignature().getName();
        Object[] args = joinPoint.getArgs();
        
        System.out.println("Entering method: " + methodName + " with args: " + Arrays.toString(args));
        
        try {
            Object result = joinPoint.proceed();
            long elapsed = System.nanoTime() - start;
            System.out.println("Method " + methodName + " completed in " + elapsed + " ns");
            return result;
        } catch (Exception e) {
            System.err.println("Exception in " + methodName + ": " + e.getMessage());
            throw e;
        }
    }
    
    @Around("execution(* com.example.service.*.transfer(..))")
    public Object auditTransfer(ProceedingJoinPoint joinPoint) throws Throwable {
        MethodSignature signature = (MethodSignature) joinPoint.getSignature();
        String methodName = signature.getName();
        
        // Audit before
        auditService.log("Starting transfer: " + methodName);
        
        try {
            Object result = joinPoint.proceed();
            auditService.log("Transfer completed successfully: " + methodName);
            return result;
        } catch (Exception e) {
            auditService.log("Transfer failed: " + methodName + " - " + e.getMessage());
            throw e;
        }
    }
}

What is Optimistic Locking in Spring Data?

Quick Answer

Preventing lost updates by versioning rows.

Detailed Explanation

Optimistic locking prevents concurrent modifications by using version fields. Internally, Hibernate compares the version in the entity with the database version before updates; if they differ, an OptimisticLockException is thrown. This approach assumes conflicts are rare and handles them at commit time.

Best practices include using @Version on numeric fields, handling exceptions gracefully in services, and considering retry mechanisms for transient conflicts. Common pitfalls involve forgetting to increment versions manually in native queries, or using optimistic locking on high-contention entities. Real-world usage scenarios include collaborative editing, financial transactions, and inventory management. Performance considerations: Adds a version check to update queries; suitable for low to medium contention, but consider pessimistic locking for high contention.

// Handling optimistic lock exceptions
@Transactional
public void updateStockWithRetry(Long productId, Integer newStock, int maxRetries) {
    for (int attempt = 0; attempt < maxRetries; attempt++) {
        try {
            updateStock(productId, newStock);
            return;  // Success
        } catch (OptimisticLockException e) {
            if (attempt == maxRetries - 1) {
                throw e;  // Last attempt failed
            }
            // Retry with fresh data
            System.out.println("Optimistic lock conflict, retrying... " + (attempt + 1));
        }
    }
}

What is Spring WebFlux?

Quick Answer

A reactive-stack web framework added in Spring 5.

Detailed Explanation

Spring WebFlux represents a paradigm shift in Spring's web framework offerings, introducing a fully reactive, non-blocking architecture designed to handle high concurrency with minimal thread usage, making it ideal for modern, scalable applications. Unlike the traditional Spring MVC, which operates on a synchronous, thread-per-request model, WebFlux leverages Project Reactor's reactive streams specification, using Mono (for 0-1 items) and Flux (for 0-N items) publishers to handle asynchronous data flows. Internally, it runs on Netty as the default server (with support for Tomcat, Jetty, and Undertow via reactive adapters), employing an event-driven, backpressure-aware model where threads are not blocked waiting for I/O operations. This allows a single thread to handle thousands of concurrent connections by suspending execution when waiting for data and resuming when it's available. The framework supports both annotation-based controllers (similar to MVC) and functional programming styles with router functions. Reactive programming introduces concepts like cold vs. hot publishers, where cold publishers create data on demand and hot publishers share data across subscribers. Best practices include avoiding blocking operations within reactive chains (use subscribeOn for I/O-bound work and publishOn for CPU-bound), implementing proper error handling with onErrorResume or onErrorContinue, and using operators like timeout, retry, and retryWhen for resilience. Handle backpressure by using onBackpressureBuffer or onBackpressureDrop to prevent memory exhaustion. Common pitfalls include accidentally introducing blocking code (e.g., calling JDBC synchronously, which defeats the purpose), misunderstanding operator behavior (like flatMap creating concurrency), or creating infinite streams without limits. In real-world scenarios, WebFlux excels in building high-throughput APIs for real-time data streaming (e.g., server-sent events for live dashboards), integrating with reactive databases like R2DBC or MongoDB's reactive driver, and creating microservices that need to handle bursty traffic. It's particularly valuable for applications dealing with external API calls, where non-blocking I/O can significantly reduce latency. Performance considerations show WebFlux can achieve 10-100x higher throughput than MVC in I/O-bound scenarios, but it requires careful resource management: monitor heap usage for unbounded streams, use connection pooling for reactive clients, and profile for blocking calls. For CPU-intensive work, consider offloading to separate thread pools. Debugging reactive applications can be challenging; use doOnNext, doOnError, and logging operators liberally, and tools like Reactor's Hooks.onOperatorDebug() for stack traces. Integration with Spring Security and other ecosystem components is seamless, allowing reactive authentication and authorization.

public class ReactiveController {

    public Mono<String> getMono() {
        return Mono.just("Hello, Reactive World!")
                   .doOnNext(data -> System.out.println("Processing: " + data))
                   .onErrorResume(e -> {
                       System.err.println("Error: " + e.getMessage());
                       return Mono.just("Error occurred: " + e.getMessage());
                   })
                   .timeout(Duration.ofSeconds(5)); // Prevent hanging
    }
    
    @GetMapping(value = "/stream", produces = "text/event-stream")
    public Flux<String> stream() {
        return Flux.interval(Duration.ofSeconds(1))
                   .map(sequence -> "Data " + sequence)
                   .take(10) // Limit to prevent infinite stream
                   .onErrorContinue((e, obj) -> System.err.println("Error in stream: " + e))
                   .doFinally(signal -> System.out.println("Stream completed with signal: " + signal));
    }

        return userService.findById(id)
                          .switchIfEmpty(Mono.error(new UserNotFoundException("User not found")))
                          .subscribeOn(Schedulers.boundedElastic()); // For blocking DB calls
    }

                          .onBackpressureBuffer(100) // Handle backpressure

    }

        return userMono
            .flatMap(user -> {
                if (user.getName() == null || user.getName().isEmpty()) {
                    return Mono.error(new IllegalArgumentException("Name cannot be empty"));
                }
                return userService.save(user);
            })
            .onErrorResume(IllegalArgumentException.class, e -> 
                Mono.error(new BadRequestException("Invalid user data")));
    }
    
    @GetMapping("/combined")
    public Mono<String> combined() {
        Mono<String> mono1 = Mono.just("Part 1").delayElement(Duration.ofMillis(100));
        Mono<String> mono2 = Mono.just("Part 2").delayElement(Duration.ofMillis(200));
        return Mono.zip(mono1, mono2)
                   .map(tuple -> tuple.getT1() + " " + tuple.getT2())
                   .timeout(Duration.ofSeconds(1))
                   .onErrorReturn("Timeout occurred");
    }
    
    @GetMapping("/parallel")
    public Flux<String> parallelProcessing() {
        List<String> items = List.of("A", "B", "C", "D");
        return Flux.fromIterable(items)
                   .parallel()
                   .runOn(Schedulers.parallel())
                   .map(item -> "Processed " + item)
                   .sequential()
                   .onErrorContinue((e, obj) -> System.err.println("Error processing " + obj + ": " + e));
    }

What is Spring WebFlux?

Quick Answer

Spring's reactive-stack web framework.

Detailed Explanation

Spring WebFlux is a reactive web framework that uses Project Reactor's Mono and Flux for asynchronous, non-blocking processing. Unlike Spring MVC's thread-per-request model, WebFlux uses an event-loop architecture with backpressure support, making it ideal for high-concurrency scenarios. Internally, it runs on Netty, Tomcat, or Jetty with reactive adapters. Best practices include using functional endpoints for simple cases, handling backpressure properly, and avoiding blocking operations. Common pitfalls include mixing blocking and non-blocking code causing performance issues, misunderstanding cold vs hot publishers, and improper error handling in reactive chains. Real-world usage includes real-time applications, microservices with high throughput requirements, and integration with reactive databases like R2DBC. Performance considerations involve monitoring reactor thread pools, using appropriate operators for data transformation, and ensuring proper resource cleanup.

What is the Spring Event mechanism?

Quick Answer

A Publish-Subscribe implementation within the Application Context.

Detailed Explanation

Spring's event mechanism provides a decoupled communication pattern using the publish-subscribe model within the ApplicationContext. Events extend ApplicationEvent, publishers use ApplicationEventPublisher, and listeners use @EventListener or implement ApplicationListener. Internally, events are synchronous by default but can be made asynchronous. Best practices include using custom event classes with relevant data, handling exceptions in listeners, and considering transactional event publishing. Common pitfalls include memory leaks from accumulating listeners, performance issues from synchronous processing of slow listeners, and race conditions in multi-threaded environments. Real-world usage includes user registration notifications, cache invalidation, audit logging, and workflow orchestration. Performance considerations involve using @Async listeners for non-critical processing, limiting listener count, and monitoring event throughput.

What is Transaction Propagation?

Quick Answer

It defines how a transaction should behave when a transactional method calls another.

Detailed Explanation

Transaction propagation in Spring defines the behavior of transactions when a transactional method invokes another, controlling whether a new transaction is created, an existing one is joined, or other actions are taken. The key propagation types are: REQUIRED (default; joins existing transaction or creates new), REQUIRES_NEW (suspends current transaction and starts a new one), NESTED (creates a sub-transaction within the current transaction, allowing partial rollback), SUPPORTS (joins existing transaction if present, runs non-transactionally otherwise), NOT_SUPPORTED (suspends current transaction if present), MANDATORY (requires existing transaction, throws exception if none), NEVER (throws exception if transaction exists). Internally, Spring uses PlatformTransactionManager (implementations like DataSourceTransactionManager for JDBC, JpaTransactionManager for JPA) and TransactionDefinition to manage propagation. The framework employs proxy-based interception via AOP to wrap methods with transactional behavior, using TransactionInterceptor to handle begin/commit/rollback. Best practices include using REQUIRED for most business methods, REQUIRES_NEW for operations that must commit independently (like audit logging), and understanding isolation levels (READ_COMMITTED, SERIALIZABLE) to prevent concurrency issues. Configure timeouts to prevent hanging transactions and use @Transactional(readOnly = true) for read-only operations to optimize performance. Common pitfalls include incorrect propagation causing data inconsistencies (e.g., using NEVER when transaction is required), forgetting rollback rules (only unchecked exceptions trigger rollback by default), or mixing propagation with asynchronous methods (transactions don't span threads). In real-world scenarios, propagation ensures data integrity in complex service layers: a payment service might use REQUIRES_NEW for audit logging to ensure logs persist even if payment fails. For microservices, consider distributed transactions with patterns like Saga or TCC. Performance considerations involve transaction overhead: each transaction adds setup/teardown time, so minimize transaction scope. Monitor with Spring Boot Actuator's transaction metrics and use connection pooling to avoid exhaustion. For reactive applications, Spring offers @Transactional support in WebFlux with TransactionalOperator. Debugging involves enabling SQL logging and checking transaction boundaries with @Transactional annotations.

Code Example
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.support.TransactionTemplate;
import org.springframework.stereotype.Service;
import org.springframework.beans.factory.annotation.Autowired;

@Service
public class TransactionService {
    
    @Autowired
    private OrderRepository orderRepository;
    
    @Autowired
    private AuditService auditService;
    
    @Autowired
    private TransactionTemplate transactionTemplate;
    
    @Transactional(propagation = Propagation.REQUIRED, isolation = Isolation.READ_COMMITTED)
    public void processOrder(Order order) {
        try {
            // Save order - part of main transaction
            orderRepository.save(order);
            
            // Audit in same transaction - if this fails, order save rolls back
            auditService.log("Order processed", order.getId());
            
            // Simulate potential failure
            if (order.getAmount() > 1000) {
                throw new RuntimeException("High value order requires approval");
            }
        } catch (Exception e) {
            // Log and rethrow - triggers rollback
            System.err.println("Error processing order: " + e.getMessage());
            throw e;
        }
    }
    
    @Transactional(propagation = Propagation.REQUIRES_NEW, 
                   rollbackFor = Exception.class, 
                   noRollbackFor = BusinessException.class)
    public void processInNewTransaction(Order order) {
        // This runs in a completely new transaction
        // Even if outer transaction rolls back, this commits
        auditService.log("Independent audit", order.getId());
        
        // Custom rollback rules
        if (someCondition()) {
            throw new BusinessException("Business rule violation");
        }
    }
    
    @Transactional(propagation = Propagation.NESTED)
    public void nestedOperation() {
        // Creates a savepoint in current transaction
        // Allows partial rollback without affecting parent
        try {
            subTaskRepository.save(new SubTask());
            if (validationFails()) {
                throw new ValidationException("Invalid subtask");
            }
        } catch (ValidationException e) {
            // Only this nested transaction rolls back
            System.err.println("Nested operation failed: " + e.getMessage());
            throw e;
        }
    }
    
    @Transactional(propagation = Propagation.SUPPORTS, readOnly = true)
    public List<Order> getOrders() {
        // Joins existing transaction if present, otherwise non-transactional
        // readOnly = true optimizes for read operations
        return orderRepository.findAll();
    }
    
    @Transactional(propagation = Propagation.MANDATORY)
    public void updateOrderStatus(Long orderId, String status) {
        // Requires existing transaction, throws exception if none
        Order order = orderRepository.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException("Order not found"));
        order.setStatus(status);
        orderRepository.save(order);
    }
    
    public void programmaticTransaction() {
        // Using TransactionTemplate for programmatic control
        transactionTemplate.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
        transactionTemplate.setIsolationLevel(TransactionDefinition.ISOLATION_SERIALIZABLE);
        transactionTemplate.setTimeout(30); // 30 seconds
        
        transactionTemplate.execute(status -> {
            try {
                // Transactional code
                auditService.log("Programmatic transaction", 0L);
                return "Success";
            } catch (Exception e) {
                status.setRollbackOnly();
                throw e;
            }
        });
    }
    
    @Transactional(propagation = Propagation.NEVER)
    public void nonTransactionalOperation() {
        // Throws exception if called within a transaction
        // Useful for operations that must never be transactional
        reportService.generateReport();
    }
}
