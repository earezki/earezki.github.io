sync.Pool usage?

Quick Answer

A thread-safe set of temporary objects that may be individually saved and retrieved. It reduces GC pressure.

Detailed Explanation

Instead of allocating new objects frequently (like HTTP request buffers), you Get() from the pool and Put() back when done. The GC can clear the pool at any time, so don't use it for valid state persistence.

Code Example

var bufPool = sync.Pool{
New: func() interface{} { return new(bytes.Buffer) },
}

CGo purpose and downsides?

Quick Answer

CGo enables Go packages to call C code. It allows reusing C libraries.

Detailed Explanation

Downsides: It complicates the build process (requires GCC), loses Go's memory safety, the call overhead is high (stack switching), and it messes with the Go scheduler (locks OS thread). Cross-compilation becomes a nightmare.

Compare RWMutex vs Mutex.

Quick Answer

RWMutex allows multiple readers OR one writer. Mutex allows only one lock holder (read or write).

Detailed Explanation

Use RWMutex when reads vastly outnumber writes. It improves concurrency for read-heavy workloads. Note that RWMutex is more expensive than Mutex, so if critical section is tiny, Mutex might be faster.

Escape Analysis?

Quick Answer

The compiler's process of deciding whether a variable should be allocated on the stack or the heap.

Detailed Explanation

If a variable's reference 'escapes' the function (e.g., returned as pointer), it must go to the heap (GC managed). If it stays local, it goes to stack (cheap). go build -gcflags '-m' shows decisions.

How does the Go Scheduler work?

Quick Answer

M:N Scheduling.

Detailed Explanation

Go multiplexes M goroutines onto N OS threads using P (Processors). It uses a work-stealing algorithm to balance load (G-M-P model).

Code Example
G (Goroutine), M (Machine/Thread), P (Processor)

Inspecting Go Scheduler internals (M, P, G model).

Quick Answer

G = Goroutine (stack, PC), M = Machine (OS Thread), P = Processor (Resource/Context required to run Go code).

Detailed Explanation

The Go scheduler maps Gs onto Ms. P is a local queue of Gs. When an M blocks (syscall), P is detached and handed to another M to keep running other Gs. This 'Work Stealing' scheduler is why Go handles thousands of concurrent connections efficiently.

Memory Leak patterns in Go?

Quick Answer

Common leaks: improperly stopped time.Tickers, goroutines waiting on nil/blocked channels, and slicing large arrays.

Detailed Explanation

Slicing pitfall: If you slice a small piece (a[0:1]) off a huge array, the huge underlying array stays in memory because the slice references it. Fix: copy the slice data to a new slice.

Race Condition detection?

Quick Answer

Go has a built-in race detector, enabled via go run -race or go test -race.

Detailed Explanation

It instruments code at compile/runtime to catch unsynchronized access to shared variables. It incurs high overhead (5-10x CPU, memory), so treat it as a testing tool, not for production.
