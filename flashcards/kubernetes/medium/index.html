emptyDir Volume?

Quick Answer

Temporary volume sharing Pod's lifespan.

Detailed Explanation

An emptyDir volume is a temporary directory created when a Pod is assigned to a Node, existing for the Pod's lifetime. Core functionality: provides shared storage between containers in the same Pod. Key features: data persists across container restarts but is lost when Pod terminates. Internal mechanics: backed by the Node's local storage (disk or memory). Architecture: simple, no persistence across Nodes. Recommended practices: use for cache, logs, or temporary data; specify medium: "Memory" for RAM-backed storage. Common mistakes: relying on it for persistent data; not handling Pod rescheduling. Practical use cases: sharing files between init containers and main containers, temporary scratch space. Performance: fast local access, but limited by Node resources. Cost: uses Node's local storage, no additional cloud costs.

Code Example
# Basic emptyDir volume
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: cache
      mountPath: /tmp/cache
  - name: sidecar
    image: busybox
    volumeMounts:
    - name: cache
      mountPath: /shared
  volumes:
  - name: cache
    emptyDir: {}

---
# Memory-backed emptyDir
apiVersion: v1
kind: Pod
metadata:
  name: memory-pod
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: ram-disk
      mountPath: /ram
  volumes:
  - name: ram-disk
    emptyDir:
      medium: Memory
      sizeLimit: 1Gi  # Optional size limit

# kubectl commands
kubectl apply -f pod.yaml
kubectl exec -it my-pod -- ls /tmp/cache
# Error handling: Check Pod status with kubectl describe pod my-pod

kubectl port-forward?

Quick Answer

Local access.

Detailed Explanation

kubectl port-forward creates secure tunnels from local ports to pod ports, enabling local access to cluster services. Core functionality establishes TCP connections through the API server. Key features include multiple port mappings and service forwarding. Internal mechanics involve API server proxying. Recommended practices include using for debugging, setting timeouts, and securing access. Common mistakes include leaving forwards running, exposing sensitive ports, or network issues. Practical use cases include local development and debugging. Performance implications include latency; cost-wise, no additional charges.

Code Example
# Basic port forwarding to pod
kubectl port-forward pod/my-pod 8080:80
# Forward to service
kubectl port-forward svc/my-service 8080:80
# Multiple ports
kubectl port-forward pod/my-pod 8080:80 8443:443
# Forward to specific pod in deployment
kubectl port-forward deployment/my-deployment 8080:80
# With namespace
kubectl port-forward -n my-namespace pod/my-pod 8080:80

kubectl port-forward pod/my-pod 8080:80 &

kill %1

kubectl port-forward pod/my-pod 8080:80 --v=4

Non-identifying metadata.

ConfigMap?

Quick Answer

Non-sensitive config.

Detailed Explanation

ConfigMaps are API objects used to store non-confidential configuration data in key-value pairs, separating configuration from application code for better portability and maintainability. Core functionality includes storing data as literals or files, which can be consumed by pods as environment variables, command-line arguments, or volume mounts. Key features include immutability by default (though updates are possible), support for binary data, and integration with other Kubernetes resources. Internal mechanics involve storing data in etcd as part of the cluster's state, with data being injected into pods at runtime by the kubelet. Recommended practices include using ConfigMaps for environment-specific settings, versioning them with Git, and avoiding sensitive data (use Secrets instead). Common mistakes include storing secrets in ConfigMaps (leading to security risks) or not handling updates properly (pods don't automatically reload changes). Practical use cases include application configurations like database URLs or feature flags. Performance implications are minimal as ConfigMaps are lightweight, but large ConfigMaps can increase pod startup time; cost-wise, they consume etcd storage space.

Code Example
# Complete ConfigMap YAML example
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-app-config
  namespace: default
data:
  # Key-value pairs for configuration
  database_url: "postgresql://db:5432/myapp"
  log_level: "info"
  # Multi-line configuration
  config.yaml: |
    server:
      port: 8080
      timeout: 30s
---
# Example kubectl commands
# Create from literals
kubectl create configmap my-config --from-literal=key1=value1 --from-literal=key2=value2
# Create from file
kubectl create configmap my-config --from-file=config.properties
# Create from directory
kubectl create configmap my-config --from-file=/path/to/dir
# View ConfigMap
kubectl get configmap my-config -o yaml
# Update ConfigMap (note: pods won't auto-reload)
kubectl patch configmap my-config --type merge -p '{"data":{"newkey":"newvalue"}}'
# Error handling: Check if ConfigMap exists before applying
kubectl apply -f configmap.yaml --dry-run=client

DaemonSet?

Quick Answer

One per node.

Detailed Explanation

DaemonSets ensure that a copy of a Pod runs on all (or a subset of) nodes in the cluster, ideal for node-level services that need to be present on every node. Core functionality guarantees one pod per node, automatically handling node additions/removals. Key features include node selectors for targeting specific nodes, tolerations for scheduling on tainted nodes, and support for rolling updates. Internal mechanics involve the DaemonSet controller monitoring nodes and creating pods accordingly, with pods being scheduled by the kube-scheduler. Recommended practices include using resource limits to prevent node resource exhaustion, implementing proper logging/monitoring, and using node selectors for selective deployment. Common mistakes include deploying resource-intensive pods (impacting node performance), not handling node taints properly, or forgetting that DaemonSets ignore unschedulable nodes. Practical use cases include logging agents (Fluentd, Filebeat), monitoring tools (Prometheus Node Exporter, Datadog), network plugins (Calico, Flannel), and security scanners. Performance implications include guaranteed resource usage per node; cost-wise, scales with cluster size.

Code Example
# Complete DaemonSet YAML example
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      containers:
      - name: node-exporter
        image: prom/node-exporter:v1.6.0
        ports:
        - containerPort: 9100
          hostPort: 9100  # Expose on host
        resources:
          limits:
            cpu: 100m
            memory: 100Mi
          requests:
            cpu: 50m
            memory: 50Mi
        volumeMounts:
        - name: proc
          mountPath: /host/proc
          readOnly: true
        - name: sys
          mountPath: /host/sys
          readOnly: true
      volumes:
      - name: proc
        hostPath:
          path: /proc
      - name: sys
        hostPath:
          path: /sys
      tolerations:
      - key: node-role.kubernetes.io/master
        effect: NoSchedule
---
# Example kubectl commands
# Deploy DaemonSet
kubectl apply -f daemonset.yaml
# Check pods on all nodes
kubectl get pods -o wide -l app=node-exporter
# Update image
kubectl set image daemonset/node-exporter node-exporter=prom/node-exporter:v1.7.0
# Limit to specific nodes
kubectl patch daemonset node-exporter --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux"}}}}}'
# Error handling: Check pod status
kubectl describe daemonset node-exporter
# Rollback update
kubectl rollout undo daemonset/node-exporter

Different Deployment Strategies?

Quick Answer

RollingUpdate (default) and Recreate.

Detailed Explanation

RollingUpdate replaces pods incrementally for zero downtime. Recreate terminates all before creating new ones, causing downtime. Core functionality: Safe updates vs simplicity. Internal mechanics: Deployment controller manages rollout. Recommended practices: Use RollingUpdate for production; set maxUnavailable/minAvailable. Common mistakes: Not testing rollbacks; ignoring resource constraints. Practical use cases: App updates, canary deployments. Performance: RollingUpdate maintains availability; cost: Extra resources during transition.

Code Example
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 3
  strategy:
    type: RollingUpdate  # Default
    rollingUpdate:
      maxUnavailable: 1  # Max pods down
      maxSurge: 1       # Extra pods during update
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: nginx:1.20
---
# Recreate strategy
  strategy:
    type: Recreate
---
# kubectl commands
kubectl apply -f deployment.yaml
kubectl rollout status deployment/my-deployment
kubectl rollout undo deployment/my-deployment  # Rollback
kubectl set image deployment/my-deployment app=nginx:1.21  # Update image

Headless Service?

Quick Answer

Direct Pod IP.

Detailed Explanation

Headless Services provide direct access to pod IPs via DNS, enabling client-side load balancing and service discovery for stateful applications. Core functionality returns individual pod IPs instead of a cluster IP. Key features include DNS A records for each pod and support for stateful sets. Internal mechanics involve DNS resolution without kube-proxy intervention. Recommended practices include using with StatefulSets, implementing client-side load balancing, and proper DNS configuration. Common mistakes include using for load-balanced services (inefficient), not handling pod IP changes, or DNS caching issues. Practical use cases include databases and distributed systems requiring direct pod access. Performance implications include reduced latency; cost-wise, no additional charges.

Code Example
# Complete Headless Service YAML
apiVersion: v1
kind: Service
metadata:
  name: headless-service
  namespace: default
spec:
  clusterIP: None  # Makes it headless
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
---
# Example StatefulSet with Headless Service
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: my-app
spec:
  serviceName: headless-service
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: myapp:latest
        ports:
        - containerPort: 8080
---
# Example kubectl commands
# Create headless service
kubectl apply -f headless-service.yaml
# Check DNS resolution
kubectl run dns-test --image=busybox --rm -it -- nslookup headless-service

kubectl run dns-test --image=busybox --rm -it -- nslookup headless-service

How to mount a ConfigMap?

Quick Answer

As Environment Variables or as a Volume.

Detailed Explanation

ConfigMaps store non-sensitive data. Mount as env vars for direct access or as volumes for file-based configs. Core functionality: Decouples config from code. Internal mechanics: Kubelet injects data into pods. Recommended practices: Use for app configs, not secrets. Common mistakes: Updating ConfigMap doesn't auto-reload pods; use subPath for single files. Practical use cases: App settings, config files. Performance: Minimal overhead; cost: Storage for large maps.

Code Example
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-config
  namespace: default
data:
  config.yaml: |
    key1: value1
    key2: value2
  app.properties: |
    db.host=localhost
---
# As Environment Variables
apiVersion: v1
kind: Pod
metadata:
  name: env-pod
spec:
  containers:
  - name: app
    image: busybox
    envFrom:

metadata:
  name: volume-pod
spec:
  containers:
  - name: app

  volumes:
  - name: config-vol
    configMap:
      name: my-config
---

HPA?

Quick Answer

Horizontal Pod Autoscaler.

Detailed Explanation

Horizontal Pod Autoscaler automatically scales pod replicas based on CPU utilization or custom metrics, ensuring optimal resource usage. Core functionality monitors metrics and adjusts replica counts. Key features include multiple metric types, scaling policies, and stabilization windows. Internal mechanics involve metrics collection and controller adjustments. Recommended practices include setting appropriate targets, using custom metrics, and configuring cooldown periods. Common mistakes include aggressive scaling (thrashing), ignoring stabilization, or wrong metric selection. Practical use cases include variable traffic applications. Performance implications include scaling delays; cost-wise, optimizes resource usage.

Code Example
# Complete HPA YAML examples
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-example
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60
---
# Custom metrics HPA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-custom
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Pods
    pods:
      metric:
        name: packets-per-second
      target:
        type: AverageValue
        averageValue: 1000
---
# Example kubectl commands
# Create HPA
kubectl apply -f hpa.yaml
# Check HPA status
kubectl get hpa
kubectl describe hpa hpa-example
# View scaling events
kubectl get events --field-selector involvedObject.kind=HorizontalPodAutoscaler
# Manually scale (temporarily)
kubectl scale deployment my-app --replicas=5
# Error handling: Check metrics
kubectl get --raw /apis/metrics.k8s.io/v1beta1/pods | jq
# Delete HPA
kubectl delete hpa hpa-example

Ingress?

Quick Answer

HTTP Router.

Detailed Explanation

Ingress is a Kubernetes API object that manages external access to services within a cluster, primarily for HTTP and HTTPS traffic, acting as a smart router and load balancer. Core functionality includes defining rules for routing traffic based on hostnames, paths, and headers, with support for SSL/TLS termination, load balancing, and URL rewriting. Key features encompass multiple backend services per Ingress, path-based routing, host-based routing, and integration with cert-manager for automatic TLS certificates. Internal mechanics rely on an Ingress controller (like nginx, traefik, or AWS ALB) that watches Ingress resources and configures the underlying load balancer or proxy. Recommended practices include using annotations for advanced features (e.g., rate limiting), keeping rules simple, and implementing proper TLS. Common mistakes include misconfigured host/path rules leading to routing errors, forgetting to install an Ingress controller, or exposing sensitive services without authentication. Practical use cases include web applications, API gateways, and microservices routing. Performance implications depend on the controller (nginx is efficient), but complex rules can increase latency; cost-wise, cloud-managed Ingress may incur provider charges.

Code Example
# Complete Ingress YAML example
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    cert-manager.io/cluster-issuer: "letsencrypt-prod"  # For TLS
spec:
  ingressClassName: nginx  # Specify controller
  tls:
  - hosts:
    - myapp.example.com
    secretName: myapp-tls  # TLS secret
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
---
# Example kubectl commands
# Apply Ingress
kubectl apply -f ingress.yaml
# Check status
kubectl get ingress my-ingress
# Describe for troubleshooting
kubectl describe ingress my-ingress
# Test routing
curl -H "Host: myapp.example.com" http://ingress-ip/api
# Error handling: Validate YAML
kubectl apply -f ingress.yaml --dry-run=client
# Update rules
kubectl patch ingress my-ingress --type merge -p '{"spec":{"rules":[{"host":"newhost.com","http":{"paths":[{"path":"/","pathType":"Prefix","backend":{"service":{"name":"new-service","port":{"number":80}}}}]}}]}}'

Key features include shared volumes, separate resource limits, and failure handling. Internal mechanics involve pod lifecycle management by kubelet. Recommended practices include using for data setup, dependency checks, and security initialization. Common mistakes include long-running init containers (delaying app start), not handling failures properly, or resource over-allocation. Practical use cases include database migrations, config generation, and certificate setup. Performance implications include startup delays; cost-wise, minimal additional resource usage.

Code Example

Job / CronJob?

Quick Answer

Batch tasks.

Detailed Explanation

Jobs create one or more Pods and ensure they run to successful completion, while CronJobs schedule Jobs to run periodically, perfect for batch processing and scheduled tasks. Core functionality for Jobs includes running pods until completion, with support for parallelism and completion counts; CronJobs add time-based scheduling. Key features encompass backoff limits for retries, active deadline seconds for timeouts, and suspend/resume capabilities for CronJobs. Internal mechanics involve the Job controller tracking pod completions and the CronJob controller creating Job instances based on cron schedules. Recommended practices include setting appropriate resource limits, using completion modes (NonIndexed vs Indexed), and implementing proper cleanup. Common mistakes include creating long-running jobs (use Deployments instead), not setting timeouts (jobs may run indefinitely), or misconfiguring cron schedules. Practical use cases include data processing pipelines, database migrations, report generation, and automated backups. Performance implications include no persistence (jobs clean up), but parallel jobs can strain resources; cost-wise, depends on execution frequency and duration.

Code Example
# Complete Job YAML example
apiVersion: batch/v1
kind: Job
metadata:
  name: pi-calculation
  namespace: default
spec:
  completions: 1  # Number of successful completions
  parallelism: 1   # Number of pods to run in parallel
  backoffLimit: 3  # Retries on failure
  activeDeadlineSeconds: 600  # Timeout
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
        resources:
          limits:
            cpu: 500m
            memory: 512Mi
      restartPolicy: Never
---
# Complete CronJob YAML example
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
  namespace: default
spec:
  schedule: "0 2 * * *"  # Daily at 2 AM
  jobTemplate:
    spec:
      template:

What is a Headless Service?

Quick Answer

A service without a ClusterIP.

Detailed Explanation

A Headless Service is defined by setting clusterIP: None in its specification. Unlike standard Services that provide load balancing through a single ClusterIP, Headless Services allow direct access to individual pods via DNS A records. Each pod gets its own DNS entry (e.g., pod-name.service-name.namespace.svc.cluster.local), enabling client-side load balancing and direct pod communication. Core functionality includes DNS-based service discovery without IP abstraction. Internal mechanics involve the kube-dns/coredns creating A records for each pod IP instead of a CNAME to the service IP. Recommended practices: Use for stateful applications like databases (e.g., MongoDB replica sets) where pods need unique identities. Common mistakes: Assuming load balancing occurs—Headless Services don't distribute traffic; clients must implement their own balancing. Practical use cases: StatefulSets for databases, peer-to-peer apps, custom load balancers. Performance implications: Lower latency due to direct pod access, but no built-in load balancing; cost: Minimal, as it doesn't require additional resources beyond DNS.

What is an InitContainer?

Quick Answer

A container that runs before the app containers start.

Detailed Explanation

InitContainers are specialized containers that run to completion before the main application containers in a pod start. They must succeed for the pod to proceed. Core functionality: Setup tasks like data initialization, dependency checks. Internal mechanics: Kubelet runs init containers sequentially, sharing volumes with main containers. Recommended practices: Use for one-time setup, keep lightweight. Common mistakes: Assuming init containers restart like main ones—they don't; not handling shared volumes properly. Practical use cases: Waiting for databases, downloading configs, setting permissions. Performance: Delays pod startup; cost: Additional image pulls/storage.

Code Example
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  initContainers:
  - name: init-db-check
    image: busybox
    command: ['sh', '-c', 'until nslookup mydb; do echo waiting for db; sleep 2; done;']
    # Wait for DB to be ready
  containers:
  - name: app
    image: myapp
    volumeMounts:
    - name: shared-data
      mountPath: /data
  volumes:
  - name: shared-data
    emptyDir: {}
---

What is Ingress?

Quick Answer

External access to services (HTTP/HTTPS).

Detailed Explanation

Ingress manages external access to Services, typically HTTP/HTTPS, acting as a reverse proxy. Core functionality: routes traffic based on host/path; supports SSL termination. Key features: load balancing, name-based virtual hosting. Internal mechanics: uses Ingress controller (e.g., Nginx); translates to load balancer config. Architecture: cluster extension, requires controller. Recommended practices: use for web apps; enable TLS. Common mistakes: forgetting controller installation; path conflicts. Practical use cases: multi-tenant apps, API gateways. Performance: depends on controller; adds latency. Cost: controller resources; cloud LB fees.
