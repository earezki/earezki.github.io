Recommended practices involve using consistent indentation, validating with tools, and using comments. Common mistakes include incorrect indentation, syntax errors, and neglecting validation. Practical use cases include defining all Kubernetes resources. Performance implications include parsing efficiency, while cost considerations involve development time.

Code Example
# Example complete YAML configuration
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: default
  labels:
    app: web-app
    version: v1.0
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web
        image: nginx:1.21
        ports:
        - containerPort: 80
        env:
        - name: ENV
          value: production
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
          limits:
            memory: "128Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /health
            port: 80
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5

Code Example

# Scale in specific namespace

# Scale using YAML
kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 5
EOF

# Check current scale
kubectl get deployment nginx -o jsonpath='{.spec.replicas}'

# Scale with validation
kubectl scale deployment nginx --replicas=5 && kubectl rollout status deployment/nginx

# Error handling
kubectl scale deployment nginx --replicas=5 2>&1 || echo "Scaling failed"

Master vs Worker Node?

Quick Answer

Master manages the cluster; Workers run applications.

Detailed Explanation

The control plane (master) manages the cluster state and makes decisions, while worker nodes run the actual workloads. Core functionality of the master includes API serving, scheduling, and state management. Internally, masters run etcd, API server, scheduler, and controller manager; workers run kubelet, kube-proxy, and container runtime. Best practices involve separating concerns and ensuring HA for masters. Common mistakes include running workloads on masters in single-node setups. Practical use cases: masters for orchestration, workers for compute. Performance: masters handle coordination overhead, workers handle application load. Cost: masters require consistent resources, workers scale with workload.

Code Example
# Get all nodes
kubectl get nodes

# Describe a node
kubectl describe node <node-name>

# Check node roles
kubectl get nodes --show-labels | grep node-role

# Get node capacity
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.capacity.cpu}{"\t"}{.status.capacity.memory}{"\n"}{end}'

# Label a node as master
kubectl label node <node-name> node-role.kubernetes.io/master=

# Error handling: Check node status
kubectl get nodes | grep -v Ready

Port Forwarding?

Quick Answer

Access internal pod/service from localhost.

Detailed Explanation

kubectl port-forward creates a secure tunnel from localhost to cluster resources, enabling local access to internal services. It bypasses service exposure. Core functionality includes secure local access. Internally, it uses kubectl as proxy. Recommended practices involve security considerations, short-term use, and proper cleanup. Common mistakes include leaving tunnels open, exposing sensitive ports, and not using authentication. Practical use cases include development and debugging. Performance implications include latency, while cost considerations involve security risks.

Code Example
# Forward local port to pod
kubectl port-forward pod/my-pod 8080:80

# Forward to service
kubectl port-forward svc/my-service 8080:80

# Forward multiple ports
kubectl port-forward pod/my-pod 8080:80 8443:443

# Forward to specific container port
kubectl port-forward deployment/my-deployment 8080

# Use different local port
kubectl port-forward pod/my-pod 9000:80

# Forward in background
kubectl port-forward pod/my-pod 8080:80 &

# Check active forwards
ps aux | grep kubectl

# Stop forwarding
pkill -f "kubectl port-forward"

# Forward with address binding
kubectl port-forward --address 0.0.0.0 pod/my-pod 8080:80

# Error handling: Check pod/service exists
kubectl get pod my-pod

# Use with browser
open http://localhost:8080

# Secure forwarding with authentication
kubectl port-forward pod/my-pod 8080:80 --server-print=true

What are Selectors?

Quick Answer

Way to filter objects by Label.

Detailed Explanation

Selectors filter Kubernetes objects based on labels, supporting equality and set-based matching. They enable dynamic resource selection. Core functionality includes label-based filtering. Internally, they're used by controllers and services. Recommended practices involve specific selectors, avoiding broad matches, and using set-based when appropriate. Common mistakes include overly broad selectors, label mismatches, and neglecting updates. Practical use cases include service discovery and workload management. Performance implications include query efficiency, while cost considerations involve selection overhead.

Code Example
# Equality-based selector
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
    environment: production
  ports:
  - port: 80
    targetPort: 8080

# Set-based selector
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
spec:
  selector:
    matchLabels:
      app: web
    matchExpressions:
    - key: environment
      operator: In
      values: [production, staging]
    - key: team
      operator: NotIn
      values: [frontend]
  template:
    metadata:
      labels:
        app: web
        environment: production
        team: backend
    spec:
      containers:
      - name: web
        image: nginx

# Use selectors in kubectl
kubectl get pods -l app=my-app

# Multiple conditions
kubectl get pods -l 'app=my-app,environment=production'

# Set-based selection
kubectl get pods -l 'environment in (production,staging)'

# Exclusion
kubectl get pods -l 'team notin (frontend)'

# Exists operator
kubectl get pods -l 'optional-label exists'

# Error handling: Check selector matches
kubectl get pods --selector='app=my-app' --show-labels

# Validate selectors
kubectl apply -f service.yaml --dry-run=client

What is a Cluster?

Quick Answer

Set of nodes running K8s.

Detailed Explanation

A Kubernetes Cluster is a set of nodes that run containerized applications managed by Kubernetes. It consists of a Control Plane (master nodes) responsible for cluster management and Worker Nodes that execute the workloads. The Control Plane includes components like the API Server (entry point for all operations), etcd (distributed key-value store for cluster state), Scheduler (assigns pods to nodes), and Controller Manager (maintains desired state). Core functionality encompasses orchestration, scaling, and self-healing of applications. Internally, components communicate via the API server and maintain consistency through etcd. Recommended practices include setting up high availability for control plane components, implementing network policies, and using RBAC for security. Common mistakes involve running single-node clusters in production, neglecting backup strategies for etcd, and failing to monitor control plane health. Practical use cases include deploying multi-tier applications, managing hybrid cloud environments, and supporting multi-tenant platforms. Performance implications include efficient pod scheduling and resource allocation, while cost considerations involve optimizing node usage and leveraging cloud provider features.

Code Example
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-container
        image: nginx:1.21

What is a Pod?

Quick Answer

The smallest deployable unit in K8s.

Detailed Explanation

A Pod is the smallest and simplest unit in the Kubernetes object model that you can create or deploy. It represents a single instance of a running process in the cluster and can contain one or more containers that share storage and network resources. Core functionality includes co-locating containers that need to work together, such as an application container and a sidecar for logging or monitoring. Internally, pods run on nodes and are managed by the kubelet, with containers within a pod sharing the same network namespace, allowing them to communicate via localhost. Recommended practices involve using single-container pods for most applications, implementing health checks (liveness and readiness probes), and setting resource requests and limits. Common mistakes include overusing multi-container pods when separate deployments would suffice, neglecting to handle pod lifecycle events properly, and failing to use anti-affinity rules to distribute pods across nodes. Practical use cases encompass running web servers, batch jobs, and tightly coupled microservices. Performance implications include efficient resource sharing within pods, while cost considerations involve optimizing container resource allocation to avoid waste.

Code Example
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: my-app
spec:
  containers:
  - name: main-container
    image: nginx:1.21
    ports:
    - containerPort: 80
    # Resource requests and limits for performance
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
    # Liveness probe for health checking

      httpGet:
        path: /
        port: 80

  - name: sidecar

    command: ['sh', '-c', 'while true; do echo $(date) >> /var/log/app.log; sleep 60; done']
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log
  volumes:
  - name: shared-logs
    emptyDir: {}

What is a ReplicaSet?

Quick Answer

It ensures a specified number of replicas are running.

Detailed Explanation

A ReplicaSet ensures a specified number of pod replicas are running at any given time, providing self-healing and scaling capabilities. Core functionality and key features: ReplicaSets maintain pod replicas and handle failures automatically. Key features include replica count management, pod template specification, and selector-based pod matching. Internal mechanics and architecture: The ReplicaSet controller monitors pods and creates/deletes them to match the desired count. It works with the scheduler for pod placement. Recommended practices and patterns: Use Deployments instead of direct ReplicaSets for updates, set appropriate replica counts, and use pod anti-affinity for distribution. Common mistakes and how to avoid them: Using ReplicaSets directly for rolling updates, not setting resource limits, or conflicting selectors. Always prefer Deployments. Practical use cases and scenarios: Maintaining application availability, horizontal scaling, and ensuring fault tolerance for stateless workloads. Performance and cost implications: Multiple replicas improve availability but increase resource usage. Balance replica count with cost considerations.

What is a Service (ClusterIP)?

Quick Answer

Stable internal IP for a set of Pods.

Detailed Explanation

A Service is an abstraction that defines a logical set of Pods and a policy by which to access them, providing a stable network endpoint. The ClusterIP type exposes the service on an internal IP within the cluster. Core functionality includes load balancing traffic across pods and service discovery. Internally, kube-proxy implements the service by maintaining network rules on nodes. Recommended practices involve using appropriate selectors, implementing health checks, and leveraging service meshes for advanced routing. Common mistakes include exposing services unnecessarily to external traffic, neglecting to update selectors after pod label changes, and failing to handle service discovery in applications. Practical use cases encompass internal microservice communication, database access, and API gateways. Performance implications include efficient load distribution, while cost considerations involve minimizing unnecessary service exposure.

Code Example
apiVersion: v1
kind: Service

  name: my-service
spec:
  selector:
    app: my-app  # Matches pods with this label
  ports:
  - protocol: TCP
    port: 80        # Service port
    targetPort: 8080  # Container port
  type: ClusterIP    # Default type, internal only

# Create the service
kubectl apply -f service.yaml

# Check service status
kubectl get services

# Get service endpoint details
kubectl describe service my-service

# Test service connectivity from a pod
kubectl run test-pod --image=busybox --rm -it -- wget -qO- http://my-service

# Example with multiple ports
apiVersion: v1
kind: Service

  name: multi-port-service

  ports:
  - name: http
    protocol: TCP
    port: 80
    targetPort: 8080
  - name: https
    protocol: TCP
    port: 443
    targetPort: 8443
  type: ClusterIP

# Error handling: If service doesn't route traffic, check pod labels
kubectl get pods --show-labels

What is Kubernetes?

Quick Answer

Container Orchestration Platform.

Detailed Explanation

Kubernetes (K8s) is an open-source platform designed to automate the deployment, scaling, and management of containerized applications. Its core functionality includes container orchestration, where it handles the lifecycle of containers across a cluster of machines, ensuring high availability, load balancing, and self-healing capabilities. What is Kubernetes?

Quick Answer

It is an open-source container orchestration platform.

Detailed Explanation

Kubernetes (K8s) is an open-source container orchestration platform that automates the deployment, scaling, and management of containerized applications. Core functionality and key features: It provides automated deployment, scaling, and operations of application containers across clusters of hosts. Key features include service discovery, load balancing, storage orchestration, self-healing, automated rollouts and rollbacks, secret and configuration management, and batch execution. Internal mechanics and architecture: Kubernetes follows a master-worker architecture with a control plane (API server, scheduler, controller manager, etcd) managing worker nodes that run pods. Practical use cases and scenarios: Ideal for microservices architectures, CI/CD pipelines, hybrid cloud deployments, and managing complex distributed systems like web applications, data processing jobs, and machine learning workloads. Performance and cost implications: Efficient resource utilization reduces costs, but over-scaling can increase expenses. What is Port Forwarding in K8s?

Quick Answer

Accessing a Pod's port locally.

Detailed Explanation

Port forwarding creates a secure tunnel from a local port to a port on a pod in the cluster. Its core functionality enables direct access to applications without exposing services externally. Internally, it uses the Kubernetes API server as a proxy. Best practices include using it for debugging and temporary access. Common mistakes involve leaving port forwards running unintentionally. Practical use cases include debugging applications, accessing databases, and testing services. Performance depends on network latency, and cost implications are minimal as it's a development tool.

Code Example
# Forward local port 8080 to pod port 80
kubectl port-forward pod/mypod 8080:80

# Forward to deployment
kubectl port-forward deployment/my-deployment 8080:80

# Forward to service
kubectl port-forward svc/my-service 8080:80

# Forward multiple ports
kubectl port-forward pod/mypod 8080:80 8443:443

# Forward in specific namespace
kubectl port-forward -n my-namespace pod/mypod 8080:80

# Background forwarding
kubectl port-forward pod/mypod 8080:80 &

# Error handling: Check if pod exists
kubectl get pod mypod -o jsonpath='{.status.phase}' || echo "Pod not found"
