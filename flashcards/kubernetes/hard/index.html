Admission Controller?

Quick Answer

API Interceptor.

Detailed Explanation

Admission Controllers are plugins that intercept requests to the Kubernetes API server after authentication and authorization but before the object is persisted to etcd. They enforce policies, validate configurations, and can mutate incoming requests. Core functionality includes mutating admission controllers (which can modify objects) and validating admission controllers (which can reject invalid requests). Internal mechanics involve webhook calls to external services or built-in logic execution within the API server. Recommended practices include using webhooks for complex logic to avoid blocking the API server, and enabling only necessary controllers to minimize overhead. Common mistakes include over-restrictive policies that block legitimate operations or ignoring error handling in webhooks. Practical use cases include enforcing security policies, defaulting resource limits, and validating custom resources. Performance implications include potential API server latency from webhook calls, so use asynchronous processing where possible; cost-wise, they add minimal overhead but may require additional infrastructure for webhook endpoints.

Code Example

metadata:
  name: example-mutating-webhook
webhooks:
- name: example.com
  clientConfig:
    service:

  rules:

    resources: ["pods"]

Cluster Autoscaler vs HPA?

Quick Answer

HPA scales Pods; Cluster Autoscaler scales Nodes.

Detailed Explanation

Horizontal Pod Autoscaler (HPA) and Cluster Autoscaler serve different scaling needs in Kubernetes. HPA automatically scales the number of pod replicas based on observed CPU utilization or other metrics, ensuring applications can handle varying loads. Cluster Autoscaler, on the other hand, adjusts the number of nodes in the cluster by adding or removing VMs when pods cannot be scheduled due to insufficient resources.

Core Functionality and Key Features: HPA provides horizontal scaling at the application level, while Cluster Autoscaler handles infrastructure scaling. HPA supports custom metrics via the metrics server or external adapters, and Cluster Autoscaler integrates with cloud providers for node management.

Internal Mechanics and Architecture: HPA uses the Metrics API to collect resource usage data and adjusts replica counts via the Scale subresource. Cluster Autoscaler runs as a deployment, monitors the scheduler for unschedulable pods, and uses cloud APIs to provision/deprovision nodes. It considers node groups, taints, and resource requests.

Recommended Practices and Patterns: Configure HPA with appropriate target utilization (e.g., 70% CPU) and cooldown periods. For Cluster Autoscaler, use node groups with similar instance types and set proper resource requests/limits on pods. Enable cluster autoscaling in managed Kubernetes services like GKE or EKS.

Common Mistakes and How to Avoid Them: Over-provisioning nodes leads to wasted costs; set minimum/maximum node counts. Ignoring pod affinity/anti-affinity can cause scheduling issues. Test autoscaling in non-production environments to avoid disruptions.

Practical Use Cases and Scenarios: HPA is used for web applications with variable traffic, while Cluster Autoscaler suits batch processing jobs or unpredictable workloads. In e-commerce, HPA scales during peak shopping hours, and Cluster Autoscaler adds nodes for data processing pipelines.

Performance and Cost Implications: HPA improves application responsiveness but may cause resource contention. Cluster Autoscaler optimizes infrastructure costs by scaling down unused nodes, though it introduces latency for node provisioning. Monitor costs closely, as over-scaling can increase expenses.

Core functionality and key features: It defines plugins for IP allocation, routing, and policy. Key features include plugin chaining, IPAM, and multi-network support. Practical use cases and scenarios: Basic networking (Flannel), advanced policy (Calico), or service mesh integration. CRD?

Quick Answer

Custom Resource Definition.

Detailed Explanation

Custom Resource Definitions (CRDs) extend the Kubernetes API by allowing users to define custom resources beyond the built-in ones like Pods and Services. Core functionality and key features: They enable the creation of custom objects that can be managed via kubectl, integrated with controllers, and stored in etcd. Key features include schema validation, subresources (status and scale), and conversion webhooks. Internal mechanics and architecture: CRDs are cluster-scoped resources that define the API group, version, and schema for custom resources. The API server validates requests against the schema and stores them. Controllers watch these resources to implement logic. Recommended practices and patterns: Use OpenAPI v3 schemas for validation, version your CRDs (e.g., v1, v1beta1), and implement conversion webhooks for version upgrades. Group related resources under the same API group. Common mistakes and how to avoid them: Defining overly broad schemas can lead to invalid resources; use strict validation. Forgetting to update controllers when changing schemas; test thoroughly. Namespace conflicts in API groups; use unique domains. Practical use cases and scenarios: Building operators for databases (e.g., PostgreSQL Operator), custom schedulers, or domain-specific applications like ML pipelines. Useful for extending Kubernetes for specific business needs. Performance and cost implications: Adds API server load due to validation; keep schemas simple. No direct cost, but complex CRDs may require more compute for controllers.

Code Example
# Complete CRD YAML example
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: myresources.example.com  # Name of the CRD
spec:
  group: example.com  # API group
  versions:
  - name: v1  # Version
    served: true  # Serve this version
    storage: true  # Store in etcd
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas:
                type: integer
                minimum: 1
                maximum: 10
            required:
            - replicas
          status:
            type: object
            properties:
              phase:
                type: string
  scope: Namespaced  # or Cluster
  names:
    plural: myresources
    singular: myresource
    kind: MyResource
    shortNames:
    - mr

# Create the CRD
kubectl apply -f crd.yaml

# Create a custom resource instance
apiVersion: example.com/v1
kind: MyResource
metadata:
  name: my-instance
spec:
  replicas: 3

# Apply with error handling
kubectl apply -f myresource.yaml --dry-run=client --validate=true

# List custom resources
kubectl get myresources

# Delete CRD (removes all instances)
kubectl delete crd myresources.example.com

How does CNI work?

Quick Answer

Container Network Interface standard.

Detailed Explanation

The Container Network Interface (CNI) is a specification and set of libraries for configuring network interfaces in Linux containers. Kubernetes uses CNI plugins to provide networking for pods, as it doesn't implement networking itself.

Core Functionality and Key Features: CNI defines how to add and remove network interfaces from containers. Plugins handle IP address assignment, routing, and network policies. Popular plugins include Calico (network policies), Flannel (simple overlay), and Cilium (eBPF-based).

Internal Mechanics and Architecture: When a pod starts, kubelet calls the CNI plugin with a JSON configuration including network name, container ID, and paths. The plugin sets up veth pairs, assigns IPs, and configures routes. It uses /etc/cni/net.d for configurations and /opt/cni/bin for binaries.

Recommended Practices and Patterns: Choose plugins based on needs (e.g., Calico for policies). Use network policies for security. Monitor network performance and ensure plugin compatibility with Kubernetes versions.

Common Mistakes and How to Avoid Them: Mismatched plugin versions can cause networking issues; keep them updated. Ignoring MTU settings may lead to packet fragmentation. Test networking in multi-node setups.

Practical Use Cases and Scenarios: In microservices architectures for service mesh integration, or in multi-tenant clusters for network isolation. Used in cloud-native applications requiring advanced networking like load balancing or encryption.

Performance and Cost Implications: Efficient plugins like Cilium use eBPF for better performance. Poorly configured networks can cause latency; optimize for throughput. Cloud provider networking may incur egress costs.

HPA vs VPA?

Quick Answer

Horizontal vs Vertical scaling.

Detailed Explanation

HPA (Horizontal Pod Autoscaler) and VPA (Vertical Pod Autoscaler) are complementary autoscaling mechanisms in Kubernetes. HPA scales pod replicas horizontally based on CPU/memory metrics or custom metrics, while VPA adjusts resource requests/limits vertically, typically requiring pod restarts. Core functionality includes HPA's support for multiple metrics (resource, external, custom) with configurable targets, and VPA's recommendation engine with modes (Off, Initial, Auto, Recreate). Key features encompass HPA's integration with metrics servers and VPA's admission controller for resource updates. Internal mechanics involve HPA watching metrics APIs and scaling deployments/statefulsets, while VPA analyzes historical usage to recommend resources. Architecture includes HPA as a standard controller and VPA as an optional admission controller. Recommended practices include using HPA for stateless workloads and VPA for stateful applications, implementing proper resource requests, and monitoring scaling events. Common mistakes include setting inappropriate target utilization causing thrashing, forgetting VPA requires restarts, or using both without coordination leading to conflicts. Practical use cases include web applications for HPA and databases for VPA. Performance implications include scaling latency for HPA and restart overhead for VPA, while cost considerations involve resource over-provisioning trade-offs and cloud provider scaling costs.

What is a Static Pod?

Quick Answer

A pod managed directly by the Kubelet on a specific node, not by the API Server.

Detailed Explanation

Static Pods are pods created and managed directly by the kubelet daemon on a node, without interaction with the Kubernetes API server. They are defined by manifest files placed in a specific directory.

Core Functionality and Key Features: Used for bootstrapping control plane components. The kubelet monitors the manifest directory and ensures the pods are running. Changes to manifests are reflected immediately.

Internal Mechanics and Architecture: Kubelet scans /etc/kubernetes/manifests (configurable) for YAML/JSON files and creates pods directly. It mirrors them to the API server for visibility but they are immutable via API. Uses the same pod lifecycle as regular pods.

Recommended Practices and Patterns: Use for etcd, kube-apiserver, etc. Keep manifests version-controlled. Avoid for application pods; use Deployments instead.

Common Mistakes and How to Avoid Them: Placing manifests in wrong directory prevents creation. Overriding with API objects can cause conflicts. Ensure kubelet has permissions.

Practical Use Cases and Scenarios: Bootstrapping self-hosted Kubernetes. Running node-specific agents or daemons.

Performance and Cost Implications: Minimal overhead as managed locally. Ensures critical components run without API dependency.

What is an Admission Controller?

Quick Answer

A piece of code that intercepts requests to the API server before persistence.

Detailed Explanation

Admission Controllers are plugins that intercept and potentially modify or reject requests to the Kubernetes API server after authentication and authorization but before the object is persisted. They enforce policies, inject defaults, and ensure compliance.

Core Functionality and Key Features: There are two types: Validating Admission Controllers reject invalid requests, while Mutating Admission Controllers modify requests (e.g., injecting sidecars or labels). They can be built-in (like PodSecurity) or custom via webhooks.

Internal Mechanics and Architecture: Controllers are compiled into the API server or run as webhooks. Mutating webhooks modify the admission request, and validating webhooks check for violations. They use the admission.k8s.io API group and can be ordered for execution.

Recommended Practices and Patterns: Use built-in controllers where possible. For custom ones, implement webhooks with proper TLS and RBAC. Test thoroughly to avoid blocking legitimate requests. Use OPA Gatekeeper for policy-as-code.

Common Mistakes and How to Avoid Them: Overly restrictive policies can break applications; start permissive and tighten gradually. Ignoring failure modes (e.g., webhook timeouts) can cause API server issues. Always validate webhook certificates.

Practical Use Cases and Scenarios: Enforce image security policies, inject logging sidecars, or validate resource limits. In regulated environments, ensure compliance with standards like PCI-DSS.

Performance and Cost Implications: Admission Controllers add latency to API requests; optimize webhook performance. They improve security but may require additional infrastructure for webhooks, increasing operational costs.

What is an Operator?

Quick Answer

A method of packaging, deploying, and managing a Kubernetes application.

Detailed Explanation

An Operator is a software extension to Kubernetes that uses custom resources to manage applications and their components. It combines Custom Resource Definitions (CRDs) to define the desired state and a custom Controller that implements the operational logic to achieve that state. The Controller encodes human operational knowledge, such as how to backup data, perform upgrades, scale resources, or handle failures, automating complex tasks that would otherwise require manual intervention.

Core Functionality and Key Features: Operators extend the Kubernetes API with domain-specific knowledge, enabling declarative management of stateful applications like databases, message queues, or monitoring systems. Key features include automated lifecycle management, self-healing capabilities, and integration with Kubernetes primitives like Services and ConfigMaps.

Internal Mechanics and Architecture: The architecture consists of a CRD that defines the custom resource schema and a Controller that watches for changes to these resources. The Controller uses the Kubernetes client-go library to interact with the API server, reconciling the current state with the desired state through a control loop. It often includes finalizers for cleanup and uses webhooks for validation.

Recommended Practices and Patterns: Use the Operator SDK or Kubebuilder for development. Follow the Operator Framework best practices, including proper RBAC, leader election for high availability, and comprehensive logging. Implement metrics and health checks for observability.

Common Mistakes and How to Avoid Them: Avoid over-engineering by starting simple; don't implement every possible feature initially. Ensure proper error handling to prevent resource leaks. Test thoroughly in staging environments, and avoid tight coupling with specific Kubernetes versions.

Practical Use Cases and Scenarios: Ideal for managing complex, stateful applications like PostgreSQL (with automated backups and failover), Prometheus (with configuration management), or Elasticsearch (with cluster scaling). Used in CI/CD pipelines for automated deployments and in multi-tenant environments for resource isolation.

Performance and Cost Implications: Operators can reduce operational overhead but may increase resource usage due to running additional controllers. They improve MTTR (Mean Time to Recovery) by automating responses to failures, potentially lowering costs through better resource utilization and reduced manual intervention.

What is CNI?

Quick Answer

Container Network Interface.

Detailed Explanation

CNI (Container Network Interface) is a specification and set of libraries for configuring network interfaces in Linux containers, serving as Kubernetes' standard for pod networking plugins. Core functionality includes IP address assignment, network isolation, and plugin chaining capabilities. Key features encompass support for multiple networking models (bridge, overlay, host-local), plugin discovery, and integration with IPAM (IP Address Management) plugins. Internal mechanics involve the kubelet calling CNI plugins during pod lifecycle events (ADD for pod creation, DEL for deletion), with plugins implementing standard CNI operations. Architecture includes a plugin-based system where each plugin handles specific networking tasks, often combined in chains. Recommended practices include choosing CNI plugins based on cluster requirements (Calico for policy, Flannel for simplicity), ensuring plugin compatibility with Kubernetes versions, and implementing network policies alongside CNI. Common mistakes involve mismatched plugin versions causing connectivity issues, improper subnet configuration leading to IP exhaustion, or failing to account for CNI overhead in resource planning. Practical use cases range from simple overlay networks in development to complex multi-tenant enterprise setups with advanced security policies. Performance implications include network latency overhead (especially with overlays) and CPU usage for encapsulation/decapsulation, while cost considerations involve licensing for commercial plugins and operational complexity of advanced features.

What is RBAC?

Quick Answer

Role-Based Access Control.

Detailed Explanation

RBAC (Role-Based Access Control) is Kubernetes' authorization mechanism that regulates access to cluster resources based on user roles rather than individual permissions. Core functionality includes defining roles (Role for namespace-scoped, ClusterRole for cluster-wide), binding roles to subjects (users, groups, service accounts) via RoleBindings or ClusterRoleBindings, and enforcing permissions through verbs (get, list, create, update, patch, delete) on API resources. Internal mechanics involve the API server checking RBAC policies during request authorization, with policies stored as cluster state. Architecture includes integration with authentication providers and support for aggregated cluster roles. Recommended practices include following principle of least privilege, using ClusterRoles sparingly, implementing regular permission audits, and leveraging role aggregation for complex scenarios. Common mistakes include granting overly broad permissions (like cluster-admin to developers), forgetting to bind roles, or misconfiguring resource names/APIGroups leading to unintended access. Practical use cases encompass multi-tenant clusters, CI/CD pipeline permissions, and operator deployments. Performance implications are minimal as RBAC checks are fast, but cost considerations involve management overhead for large numbers of roles/bindings in complex organizations.

Code Example
# Complete RBAC configuration example
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]  # "" indicates the core API group
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: jane  # Name of the user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

# Apply the RBAC configuration
kubectl apply -f rbac-role.yaml

# Verify permissions (should succeed)
kubectl get pods --as=jane

# Error handling: Check for RBAC errors
kubectl auth can-i get pods --as=jane
# Output: yes/no

# Another example: ClusterRole for cluster-wide access
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-admin
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-admin-binding
subjects:
- kind: User
  name: admin-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-admin
  apiGroup: rbac.authorization.k8s.io

What is the Controller Manager?

Quick Answer

It runs controller processes.

Detailed Explanation

The Controller Manager is a core component of the Kubernetes Control Plane responsible for running controller processes that regulate the state of the cluster. Key controllers include the Node Controller (manages node lifecycle and handles node failures), Replication Controller (ensures desired number of pod replicas), Job Controller (manages batch jobs), and Endpoint Controller (maintains endpoint objects for services). Internally, it operates as a control loop that watches the Kubernetes API server for changes in desired state versus current state, then takes corrective actions. Architecture-wise, it runs as a single process with multiple controller goroutines, typically deployed as a pod in the kube-system namespace with high availability via leader election. Recommended practices include monitoring controller performance metrics, ensuring proper RBAC permissions for controllers, and avoiding custom controllers that conflict with built-in ones. Common mistakes involve misconfiguring controller parameters (like node monitor grace period) leading to premature pod evictions, or failing to account for controller resource limits causing control plane instability. Practical use cases include automated pod rescheduling on node failures, maintaining service endpoints, and handling cron jobs. Performance implications include CPU/memory overhead from constant API server polling, while cost considerations involve ensuring controller manager pods have adequate resource requests to prevent throttling in resource-constrained environments.
