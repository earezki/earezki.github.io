Quick Answer

ClassLoaders translate a class name into a Class class instance. They follow a delegation model: Bootstrap -> Platform/Extension -> System/Application.

Detailed Explanation

When a loader is asked to load a class, it delegates the request to its parent. Only if the parent fails does it attempt to load it itself. This ensures core Java classes (like String) are always loaded by the Bootstrap loader, preventing security spoofing.

How did the introduction of the Java Module System (Project Jigsaw) change class loading and dependency management?

Quick Answer

It introduced strong encapsulation, explicit dependencies, and improved security in module boundaries.

Detailed Explanation

Before modules, Java applications relied on the classpath, which led to issues like JAR hell and unintentional access to internal APIs. The Module System allows developers to define modules with explicit exports and requires clauses, enforcing strong encapsulation at both compile-time and runtime. This reduces accidental dependencies, improves maintainability, and enhances security by limiting access to internal implementation details.     exports com.example.myapp.api;
}

How do Java's ReentrantLock and synchronized differ in terms of capabilities and behavior?

Quick Answer

ReentrantLock offers more advanced control (tryLock, fairness, interruptibility) while synchronized is simpler and JVM-managed.

Detailed Explanation

Both mechanisms provide mutual exclusion, but they operate at different levels of sophistication. synchronized is a built-in monitor lock managed entirely by the JVM, which means it automatically handles lock acquisition and release, including in exception cases. ReentrantLock is a more flexible library-based lock that allows timed lock attempts, non-blocking lock checks, interruptible waits, and configurable fairness. It must be manually unlocked, which adds both power and responsibility. The two choices reflect a trade-off: simplicity versus fine-grained control.

Code Example
ReentrantLock lock = new ReentrantLock(true); // fair lock

void update() {
    if (lock.tryLock()) {
        try {
            // critical section
        } finally {
            lock.unlock();
        }
    }
}

How does the JVM's generational garbage collection strategy optimize memory management?

Quick Answer

It separates objects by age and optimizes each region differently, reducing GC overhead.

Detailed Explanation

The JVM typically splits the heap into young and old generations. Most objects die young, so the young generation is collected frequently using fast algorithms like copying collection. Surviving objects are promoted into the old generation, where more complex but less frequent collection runs. This two-tier design reduces pauses, improves cache locality, and avoids scanning long-lived objects repeatedly. Modern collectors (G1, ZGC, Shenandoah) refine this idea with regionalized heaps and concurrent phases.

Code Example
// JVM options example (not code execution):
// -XX:+UseG1GC
// -XX:MaxGCPauseMillis=50

Under the Java Memory Model, what guarantees does volatile provide and what does it not provide?

Quick Answer

It guarantees visibility and prevents reordering, but it does not provide atomic compound operations.

Detailed Explanation

volatile ensures that reads and writes hit main memory directly rather than cached thread-local copies. This prevents stale values and enforces a strict happens-before ordering for volatile accesses. However, it does not make multi-step operations like incrementing atomic, because those involve separate read and write actions. For atomicity across compound operations, Java requires heavier tools such as Atomic* classes or locks.

Code Example
volatile int counter = 0;

// This is NOT atomic:
void increment() {
    counter++; // read + add + write
}
