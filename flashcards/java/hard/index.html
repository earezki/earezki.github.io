IdentityHashMap?

Quick Answer

Uses == reference equality instead of equals().

Detailed Explanation

IdentityHashMap uses reference equality (==) for keys, not object equality. Core functionality: identity-based mapping. Key features: allows duplicate keys by equality but different by identity. Internally, uses linear probing, system identity hash code. Architecture: not based on standard Map contract. Recommended practices: use for identity-based relationships. Common mistakes: expecting equals() behavior. To avoid, document usage clearly. Practical use cases: object graphs, proxy mappings, serialization. Performance implications: faster for identity checks. Cost implications: higher memory usage due to probing.

Code Example
import java.util.IdentityHashMap;
import java.util.HashMap;
import java.util.Map;

public class IdentityHashMapExample {
    public static void main(String[] args) {
        // Regular HashMap uses equals()
        Map<String, Integer> hashMap = new HashMap<>();
        hashMap.put(new String("key"), 1);
        hashMap.put(new String("key"), 2); // Overwrites
        System.out.println("HashMap size: " + hashMap.size()); // 1
        
        // IdentityHashMap uses ==
        Map<String, Integer> identityMap = new IdentityHashMap<>();
        identityMap.put(new String("key"), 1);
        identityMap.put(new String("key"), 2); // Different instances
        System.out.println("IdentityHashMap size: " + identityMap.size()); // 2
        
        // Useful for topology preservation
        Object obj = new Object();
        identityMap.put(obj, 100);
        System.out.println("Contains key: " + identityMap.containsKey(obj)); // true
        
        // Serialization example
        identityMap.put("proxy1", 1);
        identityMap.put("proxy2", 2);
        System.out.println("Identity map: " + identityMap);
    }
}

This example contrasts IdentityHashMap with HashMap and shows practical usage.

PhantomReference usage?

Quick Answer

To schedule post-mortem cleanup actions.

Detailed Explanation

PhantomReference is a type of weak reference that allows tracking objects after they become unreachable but before their memory is reclaimed. Core functionality includes enqueueing the reference only after finalization, with get() always returning null. Key features: no strong reference to the referent, used for cleanup without resurrecting objects. Internally, it works with a ReferenceQueue to notify when the object is about to be garbage collected. Architecture: Extends WeakReference but differs in timing - enqueued after finalize() but before reclamation. Recommended practices: use for resource cleanup like file handles or native memory, replacing finalize(). Common mistakes: trying to access the referent (always null) or not using a ReferenceQueue. To avoid, always poll the queue in a separate thread. Practical use cases: managing off-heap memory in libraries like Netty, or implementing custom cleanup for database connections. Performance implications: low overhead, but requires background thread for queue processing. Cost implications: minimal, but adds complexity to garbage collection monitoring.

Code Example
import java.lang.ref.PhantomReference;
import java.lang.ref.ReferenceQueue;
import java.io.Closeable;
import java.io.IOException;

public class PhantomReferenceExample {
    static class Resource implements Closeable {
        private final String name;
        
        Resource(String name) {
            this.name = name;
        }
        
        @Override
        public void close() throws IOException {
            System.out.println("Cleaning up resource: " + name);
        }
    }
    
    static class ResourceCleaner extends PhantomReference<Resource> implements Runnable {
        private final Closeable resource;
        
        ResourceCleaner(Resource referent, ReferenceQueue<? super Resource> q) {
            super(referent, q);
            this.resource = referent;
        }
        
        @Override
        public void run() {
            try {
                resource.close();
            } catch (IOException e) {
                System.err.println("Error closing resource: " + e.getMessage());
            }
        }
    }
    
    public static void main(String[] args) {
        ReferenceQueue<Resource> queue = new ReferenceQueue<>();
        
        Resource res = new Resource("MyResource");
        PhantomReference<Resource> phantom = new ResourceCleaner(res, queue);
        
        // Clear strong reference
        res = null;
        
        // Force GC
        System.gc();
        
        // Process queue in background thread
        new Thread(() -> {
            try {
                while (true) {
                    PhantomReference<?> ref = (PhantomReference<?>) queue.remove();
                    if (ref instanceof Runnable) {
                        ((Runnable) ref).run();
                    }
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }).start();
        
        // Wait a bit
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

This example shows a complete implementation with a cleaner class that implements Runnable for post-mortem cleanup, including error handling and a background processing thread.

ThreadLocal Memory Leak?

Quick Answer

Happens in thread pools when ThreadLocal is not removed.

Detailed Explanation

ThreadLocal variables store data per thread, with each thread maintaining its own copy. The core functionality involves associating a value with a thread, accessible via ThreadLocal.get() and set(). Key features include thread isolation and lazy initialization. Internally, values are stored in a ThreadLocalMap within each Thread object, using weak references for keys to allow garbage collection. Architecture-wise, it's a map where keys are ThreadLocal instances and values are the thread-specific data. Recommended practices include always calling ThreadLocal.remove() after use, especially in thread pools, to prevent memory leaks. Common mistakes involve forgetting to remove values, leading to retained references that prevent garbage collection. To avoid this, use try-finally blocks or ThreadLocal.withInitial() for better management. Practical use cases include storing user context in web applications or database connections in multi-threaded environments. Performance implications: ThreadLocal access is fast (O(1)), but excessive use can increase memory footprint and complicate debugging. Cost implications: In thread pools, leaked ThreadLocals can cause memory leaks proportional to the number of threads and their lifespan.

Code Example
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ThreadLocalExample {
    private static final ThreadLocal<String> threadLocal = ThreadLocal.withInitial(() -> "default");

    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(2);

        for (int i = 0; i < 5; i++) {
            executor.submit(() -> {
                try {
                    threadLocal.set("Task-" + Thread.currentThread().getId());
                    System.out.println("Thread " + Thread.currentThread().getId() + ": " + threadLocal.get());
                    // Simulate work
                    Thread.sleep(100);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    System.err.println("Task interrupted: " + e.getMessage());
                } finally {
                    // Always remove to prevent memory leaks
                    threadLocal.remove();
                }
            });
        }

        executor.shutdown();
        try {
            if (!executor.awaitTermination(5, java.util.concurrent.TimeUnit.SECONDS)) {
                executor.shutdownNow();
            }
        } catch (InterruptedException e) {
            executor.shutdownNow();
            Thread.currentThread().interrupt();
        }
    }
}

This example demonstrates proper ThreadLocal usage with removal in a finally block to avoid leaks. It also includes error handling for interruptions.

VarHandle?

Quick Answer

A typed reference to a variable for atomic operations.

Detailed Explanation

VarHandle provides typed, safe access to variables for atomic operations, replacing Unsafe. Core functionality: variable access with memory ordering semantics. Key features: acquire/release, opaque, volatile modes. Internally, uses MethodHandles for type safety. Architecture: part of java.lang.invoke package. Recommended practices: use for low-level concurrent programming. Common mistakes: confusing with reflection. To avoid, understand memory models. Practical use cases: custom concurrent data structures. Performance implications: similar to Unsafe but safer. Cost implications: API complexity, but better maintainability.

Code Example
import java.lang.invoke.VarHandle;
import java.lang.invoke.MethodHandles;

public class VarHandleExample {
    private volatile int value = 0;
    
    private static final VarHandle VALUE_HANDLE;
    
    static {
        try {
            VALUE_HANDLE = MethodHandles.lookup().findVarHandle(
                VarHandleExample.class, "value", int.class);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
    
    public void increment() {
        // Atomic increment with acquire/release semantics
        int oldValue;
        do {
            oldValue = (int) VALUE_HANDLE.getAcquire(this);
        } while (!VALUE_HANDLE.compareAndSet(this, oldValue, oldValue + 1));
    }
    
    public int getValue() {
        return (int) VALUE_HANDLE.getVolatile(this);
    }
    
    public static void main(String[] args) {
        VarHandleExample example = new VarHandleExample();
        example.increment();
        System.out.println("Value: " + example.getValue());
    }
}

This example shows VarHandle for atomic operations with proper memory barriers.

Are Java Records immutable?

Quick Answer

Shallow immutable.

Detailed Explanation

Records provide shallow immutability - final fields but mutable internal state. Core functionality: concise class definition with auto-generated methods. Key features: compact constructor, accessor methods, equals/hashCode/toString. Internally, final fields prevent reassignment. Architecture: compiler-generated implementation. Recommended practices: use for data carriers, avoid mutable components. Common mistakes: assuming deep immutability. To avoid, make components immutable too. Practical use cases: DTOs, data classes. Performance implications: memory efficient, fast equality. Cost implications: less flexible than regular classes.

Code Example
import java.util.List;
import java.util.ArrayList;

public record Person(String name, List<String> hobbies) {
    // Compact constructor for validation
    public Person {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Name cannot be null or blank");
        }
        // Defensive copy for mutable components
        hobbies = hobbies == null ? List.of() : List.copyOf(hobbies);
    }
    
    // Custom method
    public boolean hasHobby(String hobby) {
        return hobbies.contains(hobby);
    }
}

class RecordExample {
    public static void main(String[] args) {
        // Immutable record
        Person person = new Person("Alice", List.of("reading", "coding"));
        System.out.println(person);
        
        // This would fail - records are shallow immutable
        // person.name = "Bob"; // Compilation error
        
        // But if hobbies were mutable, this could modify internal state
        List<String> mutableHobbies = new ArrayList<>(List.of("reading"));
        Person person2 = new Person("Bob", mutableHobbies);
        // person2.hobbies().add("gaming"); // This would fail because hobbies is copied
        
        System.out.println("Has coding hobby: " + person.hasHobby("coding"));
        
        // Records auto-generate equals, hashCode, toString
        Person person3 = new Person("Alice", List.of("reading", "coding"));
        System.out.println("Equal persons: " + person.equals(person3));
    }
}

This example demonstrates record immutability, defensive copying, and auto-generated methods.

C1 vs C2 Compiler?

Quick Answer

Client (Fast startup) vs Server (High optimization) JIT compilers.

Detailed Explanation

C1 and C2 are the two JIT compilers in HotSpot JVM. C1 focuses on fast compilation for quick startup, C2 on aggressive optimizations for long-running applications. Core functionality: compile bytecode to native code at runtime. Key features: C1 uses simple optimizations, C2 applies advanced techniques like inlining and loop unrolling. Internally, tiered compilation starts with interpreter, then C1, then C2. Architecture: separate compilers with different optimization levels. Recommended practices: use tiered compilation (default) for balanced performance. Common mistakes: forcing C2 only, which slows startup. To avoid, let JVM choose automatically. Practical use cases: client apps need fast startup (C1), servers need peak performance (C2). Performance implications: C1 faster compilation but less optimized code, C2 slower compilation but better runtime performance. Cost implications: CPU time for compilation vs execution speed.

Code Example
# Enable tiered compilation (default)
java -XX:+TieredCompilation MyApp

# Force C1 only (fast startup)
java -XX:TieredStopAtLevel=1 MyApp

# Force C2 only (high optimization, slow startup)
java -XX:TieredStopAtLevel=4 MyApp

# Disable tiered compilation
java -XX:-TieredCompilation MyApp

These examples show different compilation configurations. Use tiered for most applications.

CGLIB vs JDK Dynamic Proxy?

Quick Answer

Class subclassing vs Interface implementation.

Detailed Explanation

JDK proxies implement interfaces, CGLIB subclasses concrete classes. Core functionality: dynamic proxy creation for AOP/interception. Key features: JDK for interfaces only, CGLIB for classes. Internally, JDK uses reflection, CGLIB bytecode generation. Architecture: different proxy mechanisms. Recommended practices: use Spring's auto-detection. Common mistakes: choosing wrong proxy type. To avoid, let frameworks decide. Practical use cases: AOP, remoting, testing. Performance implications: CGLIB slightly faster, JDK more compatible. Cost implications: CGLIB requires additional library.

Code Example
import net.sf.cglib.proxy.Enhancer;
import net.sf.cglib.proxy.MethodInterceptor;
import net.sf.cglib.proxy.MethodProxy;
import java.lang.reflect.Proxy;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;

// JDK Dynamic Proxy
interface Service {
    void execute();
}

class RealService implements Service {
    public void execute() {
        System.out.println("Real service executing");
    }
}

class JDKProxyHandler implements InvocationHandler {
    private final Service target;
    
    JDKProxyHandler(Service target) {
        this.target = target;
    }
    
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("JDK Proxy: Before method");
        Object result = method.invoke(target, args);
        System.out.println("JDK Proxy: After method");
        return result;
    }
}

// CGLIB Proxy
class CGLIBInterceptor implements MethodInterceptor {
    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy) throws Throwable {
        System.out.println("CGLIB Proxy: Before method");
        Object result = proxy.invokeSuper(obj, args);
        System.out.println("CGLIB Proxy: After method");
        return result;
    }
}

public class ProxyExample {
    public static void main(String[] args) {
        // JDK Proxy
        Service jdkProxy = (Service) Proxy.newProxyInstance(
            Service.class.getClassLoader(),
            new Class<?>[]{Service.class},
            new JDKProxyHandler(new RealService())
        );
        jdkProxy.execute();
        
        // CGLIB Proxy
        Enhancer enhancer = new Enhancer();
        enhancer.setSuperclass(RealService.class);
        enhancer.setCallback(new CGLIBInterceptor());
        RealService cglibProxy = (RealService) enhancer.create();
        cglibProxy.execute();
    }
}

This example shows both JDK and CGLIB proxy implementations with proper setup.

Compare and Swap (CAS)?

Quick Answer

An atomic instruction used to achieve lock-free synchronization.

Detailed Explanation

CAS is a hardware-level atomic operation that compares a memory location with an expected value and updates it to a new value if they match, all in one uninterruptible step. It's the foundation for lock-free data structures in java.util.concurrent.atomic. Internal mechanics: Uses CPU instructions like cmpxchg; retries on failure. Key features: Non-blocking, avoids locks. Recommended practices: Use Atomic* classes; handle ABA problem with AtomicStampedReference. Common mistakes: Ignoring ABA (old value matches but state changed); infinite loops without backoff. Use cases: Counters, flags, lock-free queues. Performance: Faster than locks for low contention; high contention may cause spinning; scales better.

Code Example
import java.util.concurrent.atomic.AtomicInteger;

public class CASEXample {
    private static AtomicInteger counter = new AtomicInteger(0);

    public static void main(String[] args) {
        // Example of increment with CAS
        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    int current;
                    int next;
                    do {
                        current = counter.get();
                        next = current + 1;
                    } while (!counter.compareAndSet(current, next)); // CAS loop
                }
            }).start();
        }

        // Wait for threads
        try {
            Thread.sleep(2000);
            System.out.println("Final count: " + counter.get());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

// Alternative: Using AtomicInteger's incrementAndGet
// counter.incrementAndGet(); // Handles CAS internally

CompletableFuture join() vs get()?

Quick Answer

Unchecked vs Checked Exception.

Detailed Explanation

join() and get() both wait for CompletableFuture completion but differ in exception handling. Core functionality and key features: Both block until the future completes, but join() throws CompletionException (unchecked) while get() throws ExecutionException (checked). Internal mechanics and architecture: join() wraps checked exceptions in CompletionException, making it suitable for functional programming. get() preserves the original exception type in ExecutionException. Recommended practices and patterns: Use join() in streams and lambdas where checked exceptions are problematic. Use get() when you need to handle specific exception types. Prefer non-blocking approaches with thenApply/thenAccept. Common mistakes and how to avoid them: Using get() in lambda expressions without proper exception handling. Not understanding that join() can still throw CompletionException. Blocking on futures in reactive code. Practical use cases and scenarios: Stream operations where exception transparency is needed. Testing asynchronous code. Composing multiple futures with allOf/anyOf. Performance and cost implications: Both have similar blocking behavior. join() avoids checked exception boilerplate in functional code.

Code Example
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutionException;
import java.util.Arrays;
import java.util.List;
import java.util.stream.Collectors;

public class CompletableFutureJoinVsGet {
    
    public static void main(String[] args) {
        // Example 1: Using get() - requires try-catch for checked exception
        CompletableFuture<String> future1 = CompletableFuture.supplyAsync(() -> {
            // Simulate async work
            return "Result from async task";
        });
        
        try {
            String result1 = future1.get(); // Blocks and throws checked ExecutionException
            System.out.println("Result 1: " + result1);
        } catch (InterruptedException | ExecutionException e) {
            System.err.println("Error with get(): " + e.getMessage());
        }
        
        // Example 2: Using join() - throws unchecked CompletionException
        CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> {
            if (Math.random() > 0.5) {
                throw new RuntimeException("Random failure");
            }
            return "Success result";
        });
        
        try {
            String result2 = future2.join(); // Cleaner in functional code
            System.out.println("Result 2: " + result2);
        } catch (Exception e) {
            System.err.println("Error with join(): " + e.getMessage());
        }
        
        // Example 3: join() in streams - much cleaner
        List<CompletableFuture<String>> futures = Arrays.asList(
            CompletableFuture.supplyAsync(() -> "Task 1"),
            CompletableFuture.supplyAsync(() -> "Task 2"),
            CompletableFuture.supplyAsync(() -> "Task 3")
        );
        
        // Using join() in stream - no checked exceptions
        List<String> results = futures.stream()
            .map(CompletableFuture::join) // Clean functional style
            .collect(Collectors.toList());
        
        System.out.println("Stream results: " + results);
        
        // Example 4: Exception handling differences
        CompletableFuture<String> failingFuture = CompletableFuture.supplyAsync(() -> {
            throw new IllegalArgumentException("Test exception");
        });
        
        // get() wraps in ExecutionException
        try {
            failingFuture.get();
        } catch (ExecutionException e) {
            System.out.println("get() caught: " + e.getCause().getClass().getSimpleName());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        
        // join() wraps in CompletionException
        try {
            failingFuture.join();
        } catch (Exception e) {
            System.out.println("join() caught: " + e.getClass().getSimpleName());
        }
    }
}

Double-Checked Locking in Singleton?

Quick Answer

An optimization to reduce synchronization overhead.

Detailed Explanation

Double-checked locking checks the singleton instance twice: once without synchronization, then again inside a synchronized block. The instance must be volatile to prevent partial construction visibility due to reordering. Core functionality: Lazy initialization with reduced lock contention. Internal mechanics: Memory barriers from volatile. Recommended practices: Use enum singletons or holder class instead for simplicity. Common mistakes: Forgetting volatile, leading to broken singletons. Use cases: Resource-heavy singletons. Performance: Avoids synchronization after initialization; volatile has slight overhead.

Code Example
public class Singleton {
    private static volatile Singleton instance; // Volatile for visibility

    private Singleton() {
        // Private constructor
    }

    public static Singleton getInstance() {
        if (instance == null) { // First check
            synchronized (Singleton.class) {
                if (instance == null) { // Second check
                    instance = new Singleton(); // Volatile ensures full construction
                }
            }
        }
        return instance;
    }

    // Example usage
    public static void main(String[] args) {
        Singleton s1 = Singleton.getInstance();
        Singleton s2 = Singleton.getInstance();
        System.out.println(s1 == s2); // true
    }
}

When a loader is asked to load a class, it delegates the request to its parent. Only if the parent fails does it attempt to load it itself. This ensures core Java classes (like String) are always loaded by the Bootstrap loader, preventing security spoofing.

Explain standard Classloader Hierarchy.

Quick Answer

Bootstrap -> Extension -> Application.

Detailed Explanation

Java's classloader hierarchy follows a delegation model for loading classes securely and efficiently. Core functionality and key features: Three main classloaders work together: Bootstrap (native), Platform/Extension, and Application/System. Each delegates to its parent before attempting to load itself. Internal mechanics and architecture: Parent delegation prevents class spoofing and ensures core classes are loaded first. Each classloader has its own namespace and can see classes from parents but not siblings. Recommended practices and patterns: Follow delegation model in custom classloaders. Use URLClassLoader for dynamic loading. Understand visibility rules for class loading. Common mistakes and how to avoid them: Breaking delegation can cause ClassCastException between classes loaded by different loaders. Not handling classloader isolation in web applications. Loading classes multiple times unnecessarily. Practical use cases and scenarios: Web application servers use custom classloaders for isolation. Plugin systems load classes dynamically. Hotswap and instrumentation tools manipulate classloading. Performance and cost implications: Delegation adds slight overhead but ensures security. Custom classloaders can impact startup time and memory usage.

Code Example
import java.net.URL;
import java.net.URLClassLoader;

public class ClassLoaderHierarchyDemo {
    
    public static void main(String[] args) {
        // Display current classloader hierarchy
        ClassLoader cl = ClassLoaderHierarchyDemo.class.getClassLoader();
        
        System.out.println("ClassLoader Hierarchy:");
        while (cl != null) {
            System.out.println(cl.getClass().getName());
            cl = cl.getParent();
        }
        System.out.println("Bootstrap ClassLoader (native code)");
        
        // Demonstrate custom classloader
        try {
            // Create a custom classloader for dynamic loading
            URL[] urls = {new URL("file:///path/to/classes/")};
            URLClassLoader customLoader = new URLClassLoader(urls, 
                ClassLoaderHierarchyDemo.class.getClassLoader());
            
            // Load a class dynamically
            Class<?> dynamicClass = customLoader.loadClass("com.example.DynamicClass");
            Object instance = dynamicClass.getDeclaredConstructor().newInstance();
            
            System.out.println("Loaded class: " + dynamicClass.getName());
            
            // Clean up
            customLoader.close();
            
        } catch (Exception e) {
            System.err.println("Error loading class: " + e.getMessage());
        }
    }
}

// Example of a simple custom classloader
class CustomClassLoader extends ClassLoader {
    
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // Implement custom loading logic here
        // This would typically read class bytes from a custom source
        throw new ClassNotFoundException(name);
    }
    
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        // Follow delegation model
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // Try parent first (delegation)
                if (getParent() != null) {
                    c = getParent().loadClass(name);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // Parent couldn't load, try ourselves
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
    
    private Class<?> findBootstrapClassOrNull(String name) {
        // Bootstrap classes are loaded by null parent
        return null;
    }
}

Explain the JVM Memory Model (Stack vs Heap).

Quick Answer

Stack stores method frames and primitives; Heap stores objects.

How do Java's ReentrantLock and synchronized differ in terms of capabilities and behavior?

Quick Answer

ReentrantLock offers more advanced control (tryLock, fairness, interruptibility) while synchronized is simpler and JVM-managed.

Detailed Explanation

Both ReentrantLock and synchronized provide mutual exclusion to prevent race conditions in concurrent Java programs, but they differ significantly in capabilities, behavior, and use cases. At its core, synchronized is a built-in language feature that uses monitor locks managed entirely by the JVM. It automatically handles lock acquisition and release, even in the presence of exceptions, through implicit try-finally blocks. This simplicity makes it suitable for straightforward synchronization needs. Internally, synchronized blocks map to monitorenter and monitorexit bytecode instructions, which interact with the JVM's thread scheduler.

In contrast, ReentrantLock is part of the java.util.concurrent.locks package and offers more advanced control. It supports non-blocking lock attempts via tryLock(), timed lock acquisition with tryLock(long, TimeUnit), interruptible waiting with lockInterruptibly(), and configurable fairness policies. Fairness ensures that threads acquire locks in the order they requested them, reducing starvation but potentially impacting performance due to increased context switching. ReentrantLock must be manually unlocked in a finally block, adding responsibility but allowing for more flexible lock management, such as conditional unlocking.

Recommended practices include using synchronized for simple cases to leverage JVM optimizations and ReentrantLock for complex scenarios requiring timeouts or interruptibility. Common mistakes involve forgetting to unlock ReentrantLock, leading to deadlocks, or using synchronized in performance-critical paths where fine-grained control is needed. Practical use cases for ReentrantLock include implementing custom synchronization primitives, producer-consumer patterns with timeouts, and scenarios where threads need to respond to interruptions. Performance implications: synchronized can be faster for uncontended locks due to JVM intrinsics, but ReentrantLock scales better under high contention with its advanced features, though fairness mode adds overhead.

Code Example
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.TimeUnit;

public class LockExample {
    private final ReentrantLock lock = new ReentrantLock(true); // Enable fairness for ordered acquisition
    private int counter = 0;

    // Example 1: Basic usage with tryLock and manual unlock
    public void increment() {
        if (lock.tryLock()) { // Non-blocking attempt
            try {
                counter++;
                System.out.println("Incremented to: " + counter);
            } finally {
                lock.unlock(); // Always unlock in finally to prevent deadlocks
            }
        } else {
            System.out.println("Could not acquire lock, skipping increment");
        }
    }

    // Example 2: Timed lock with interruptibility
    public void updateWithTimeout() {
        try {
            if (lock.tryLock(1, TimeUnit.SECONDS)) { // Wait up to 1 second
                try {
                    // Simulate critical section work
                    Thread.sleep(100);
                    counter *= 2;
                    System.out.println("Updated to: " + counter);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt(); // Restore interrupt status
                    System.out.println("Operation interrupted");
                } finally {
                    lock.unlock();
                }
            } else {
                System.out.println("Timeout acquiring lock");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            System.out.println("Interrupted while waiting for lock");
        }
    }

    // Example 3: Comparison with synchronized
    private final Object syncLock = new Object();
    
    public synchronized void syncIncrement() { // JVM-managed lock
        counter++;
        System.out.println("Synchronized increment to: " + counter);
    }

    public void syncUpdateWithTimeout() {
        synchronized (syncLock) {
            try {
                Thread.sleep(100);
                counter *= 2;
                System.out.println("Synchronized update to: " + counter);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }
}

// Usage in main method (for demonstration)
public class Main {
    public static void main(String[] args) {
        LockExample example = new LockExample();
        
        // Run in multiple threads to demonstrate concurrency
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                example.increment();
                try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }
        });
        
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                example.updateWithTimeout();
                try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }
        });
        
        t1.start();
        t2.start();
        
        try {
            t1.join();
            t2.join();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

How does the JVM's generational garbage collection strategy optimize memory management?

Quick Answer

It separates objects by age and optimizes each region differently, reducing GC overhead.

Detailed Explanation

The JVM's generational garbage collection (GC) strategy is a cornerstone of efficient memory management in Java, based on the weak generational hypothesis that most objects die young. Core functionality divides the heap into generations: the young generation (Eden and survivor spaces) for new objects, and the old generation for long-lived objects. This separation allows different collection strategies optimized for each region's characteristics.

Internal mechanics involve minor GCs (young generation only) using fast copying algorithms that move surviving objects between survivor spaces or promote them to the old generation. Major GCs handle the old generation with more thorough but slower mark-sweep-compact algorithms. Modern collectors like G1, ZGC, and Shenandoah build on this by dividing the heap into regions and performing concurrent marking and compaction to minimize pauses.

Recommended practices include tuning heap sizes, choosing appropriate collectors for application needs, and monitoring GC logs. Common mistakes involve setting heap sizes too small (causing frequent GC) or too large (increasing pause times), or ignoring GC tuning in performance-critical applications. Practical use cases range from web servers needing low latency to batch processing tolerating longer pauses. Performance implications: generational GC reduces average GC time by focusing effort on short-lived objects, but can lead to fragmentation in the old generation. Concurrent collectors trade some throughput for lower latency, with ZGC achieving sub-millisecond pauses for heaps up to 16TB.

Code Example
import java.lang.StackWalker;
import java.util.stream.Collectors;

public class StackWalkerExample {
    public static void main(String[] args) {
        method1();
    }
    
    private static void method1() {
        method2();
    }
    
    private static void method2() {
        // Efficient stack walking
        String stackTrace = StackWalker.getInstance()
            .walk(frames -> frames
                .map(StackWalker.StackFrame::toString)
                .collect(Collectors.joining("\n")));
        
        System.out.println("Stack trace:\n" + stackTrace);
        
        // Get caller class
        Class<?> callerClass = StackWalker.getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE)
            .getCallerClass();
        System.out.println("Caller class: " + callerClass.getName());
        
        // Check for specific method in stack
        boolean hasMethod1 = StackWalker.getInstance()
            .walk(frames -> frames.anyMatch(frame -> "method1".equals(frame.getMethodName())));
        
        System.out.println("Has method1 in stack: " + hasMethod1);
    }
}

Under the Java Memory Model, what guarantees does volatile provide and what does it not provide?

Quick Answer

It guarantees visibility and prevents reordering, but it does not provide atomic compound operations.

Detailed Explanation

The Java Memory Model (JMM) defines how threads interact through memory, ensuring visibility and ordering of operations. The volatile keyword provides critical guarantees for shared variables in concurrent programs. Core functionality includes ensuring that reads and writes to a volatile variable are atomic at the variable level and always hit main memory, preventing thread-local caching that could lead to stale values. It establishes a happens-before relationship: all writes before a volatile write are visible to threads that read the volatile variable afterward, and all reads after a volatile read see the effects of prior volatile writes.

Internally, volatile variables use memory barriers (fences) to prevent compiler and CPU reordering, ensuring sequential consistency for volatile accesses. However, it does not provide atomicity for compound operations like increment (read-modify-write), as these involve multiple steps that can interleave between threads. Recommended practices include using volatile for flags, single assignments, or simple state changes, but combining it with synchronization for complex operations. Common mistakes involve assuming volatile makes operations atomic, leading to race conditions in increments or checks-then-acts.

Practical use cases include implementing simple thread-safe flags (e.g., shutdown signals), double-checked locking (though now less common with better alternatives), and ensuring visibility in publish-subscribe patterns. Performance implications: volatile adds minimal overhead compared to regular variables due to memory barriers, but it's more expensive than non-volatile access. For atomic compound operations, use Atomic* classes like AtomicInteger, which leverage CPU-level atomic instructions for better performance and correctness.

Code Example
import java.util.concurrent.atomic.AtomicInteger;

public class VolatileExample {
    // Volatile for visibility, but not atomicity
    private volatile int counter = 0;
    private volatile boolean shutdown = false;
    
    // Example 1: Volatile flag (safe)
    public void shutdown() {
        shutdown = true; // Visible to all threads immediately
    }
    
    public void worker() {
        while (!shutdown) { // Reads latest value
            // Do work
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
        System.out.println("Worker shutting down");
    }
    
    // Example 2: Non-atomic increment (unsafe with volatile alone)
    public void increment() {
        counter++; // This is read + increment + write - NOT atomic!
        // Can lose updates in concurrent access
    }
    
    public int getCounter() {
        return counter;
    }
    
    // Example 3: Proper atomic increment using AtomicInteger
    private final AtomicInteger atomicCounter = new AtomicInteger(0);
    
    public void safeIncrement() {
        int newValue = atomicCounter.incrementAndGet(); // Atomic operation
        System.out.println("Safely incremented to: " + newValue);
    }
    
    public int getAtomicCounter() {
        return atomicCounter.get();
    }
    
    // Example 4: Double-checked locking with volatile (legacy pattern)
    private volatile Singleton instance;
    
    public Singleton getInstance() {
        if (instance == null) { // First check (no lock)
            synchronized (this) {
                if (instance == null) { // Second check (with lock)
                    instance = new Singleton(); // Volatile ensures visibility
                }
            }
        }
        return instance;
    }
    
    private static class Singleton {
        // Singleton implementation
    }
}

// Usage demonstration
public class Main {
    public static void main(String[] args) {
        VolatileExample example = new VolatileExample();
        
        // Demonstrate unsafe counter
        Thread[] threads = new Thread[10];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 100; j++) {
                    example.increment();
                }
            });
            threads[i].start();
        }
        
        for (Thread t : threads) {
            try {
                t.join();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
        
        System.out.println("Final counter (may be < 1000 due to races): " + example.getCounter());
        
        // Demonstrate safe counter
        for (int i = 0; i < 1000; i++) {
            example.safeIncrement();
        }
        
        System.out.println("Final atomic counter: " + example.getAtomicCounter());
    }
}
